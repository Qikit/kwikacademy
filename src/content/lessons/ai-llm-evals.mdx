## Зачем это

В прошлом уроке ты проектировал контекст агента и в конце практикума отвечал, каким замером проверишь своё решение. А как ты проверил последнюю правку своего промпта? Скорее всего, отправил три запроса, прочитал ответы и решил, что стало лучше.

Три ответа мало что доказывают. Модель отвечает с разбросом, то есть на один запрос даёт разные ответы, и на трёх примерах может повезти. А правка, которая починила один случай, способна тихо сломать два других, и узнаешь ты об этом от пользователей. Собрать свои примеры мешает мысль, что их нужны сотни. В статье инженеров Anthropic о замерах агентов хорошим началом названы 20–50 простых примеров, собранных из настоящих провалов.

После урока ты сможешь собрать мини-набор своих примеров с критерием и проверять им каждое изменение промпта или модели.

## Ядро: «стало лучше» должно быть числом

<Callout type="purple" title="Суть">
**Замер** складывается из трёх частей. Это **набор** своих примеров, **критерий**, по которому решают, хорош ли ответ, и прогон системы по набору, после которого остаётся число. В документации и статьях замер называют eval (от evaluation, «оценка»). Поменял промпт, модель или поиск — прогоняешь набор заново и сравниваешь числа.
</Callout>

Замер похож на юнит-тесты, только результат у него — доля, например «27 из 30». В уроке про семплинг прогоном назывался один запуск запроса, здесь **прогон** — один проход системы по всему набору.

Прежде чем раскрыть ответ, ответь сам, хотя бы про себя.

<Reveal q="Коллега переписал промпт бота поддержки и показывает пять ответов старой версии и пять ответов новой, на других вопросах. Новые выглядят лучше. Можно выкатывать?">
Рано. Вопросы разные, поэтому сравнились вопросы, а не промпты: новой версии могли достаться лёгкие. И пять удачных ответов могут оказаться везением. Обе версии прогоняют по одному набору и судят по критерию, который записан до прогона.
</Reveal>

## Как устроено: набор, критерий, прогон

**Набор примеров** — это входы, для которых ты заранее знаешь, каким должен быть ответ. Тридцать отзывов, каждому из которых человек поставил метку тональности, — набор. Метка служит **эталоном** (ground truth), то есть заведомо верным ответом для сверки. Двадцать вопросов к боту по документации, где для каждого записано, какой факт обязан прозвучать, — тоже набор, хотя дословного эталона нет. А сотня запросов из лога без ожидаемых ответов набором ещё не стала: сравнивать результат не с чем.

Документация Anthropic советует, чтобы набор повторял настоящий поток запросов и включал **крайние случаи**: пустой или посторонний ввод, слишком длинный текст, двусмысленность, о которой спорят и люди. Статья Anthropic о замерах агентов добавляет второй источник примеров — очередь поддержки и баг-трекер. Она про агентов, но замер одного запроса сама называет простым случаем: запрос, ответ, проверка. Ухудшение после правки называют **регрессом**, а провал из прода, занесённый в набор, — **регресс-тестом**. Вернётся ошибка — следующий прогон её покажет. Каждому примеру сразу приписывают группу: простой, сложный, сарказм, прошлый провал.

Неточность даёт и сам набор: он только выборка из запросов, которые придут в прод. По формуле из статьи Miller (2024, препринт) результат 24 из 30 — это 80 % плюс-минус примерно 14 процентных пунктов при уровне доверия 95 %. Прикидка грубая: формула рассчитана на большие наборы и на случайную выборку, а твой набор подобран руками. Поэтому число набора годится сравнивать версии, а не обещать качество в проде. Пока интервалы двух версий пересекаются, разница может оказаться разбросом. Чтобы это выяснить, Miller советует отправлять каждый пример по нескольку раз и сравнивать версии по каждому примеру.

## Как устроено: кто выносит вердикт

**Критерий** — правило, по которому ответ получает вердикт «прошёл» или «не прошёл». «Метка совпала с эталоном» — критерий. «В ответе названа верная статья договора и нет фактов, которых нет в источнике» — тоже. А «ответ должен быть хорошим» критерием не служит. По мерке из статьи об агентах, хорош тот пример с критерием, по которому два специалиста независимо придут к одному вердикту, а здесь они разойдутся.

Выносить вердикт можно тремя способами. По документации Anthropic, из подходящих берут самый быстрый и надёжный.

- **Проверка кодом.** Сверка с эталоном, поиск обязательной фразы, разбор JSON, запуск сгенерированной программы. Быстро, дёшево и воспроизводимо, но оттенков код не видит и может забраковать верный ответ в непривычной записи.
- **Человек.** Самая гибкая и качественная проверка, но медленная и дорогая. Людей зовут выборочно, чтобы сверять с ними автоматику.
- **LLM-судья** (LLM-as-judge). Это отдельный запрос к модели. Она получает ответ и **рубрику**, то есть письменные условия вердикта, и решает по ним. Судье по силам «мягкое» качество: тон, связность, опора на источник. Он дороже кода и сам отвечает с разбросом.

Для судьи документация даёт три совета. Рубрика должна быть подробной и однозначной, например «в первом предложении названа компания Acme Inc., иначе ответ неверен». Вердикт берётся из закрытого списка или ставится по шкале от 1 до 5. Перед вердиктом судья рассуждает: у Opus 5.5 рассуждение включено всегда, а думать ли над простым вердиктом, модель решает сама. Там же совет судить другой моделью, чем та, что отвечала. Статья об агентах добавляет два приёма: разрешить судье ответ «не знаю» и проверять одним запросом одно свойство.

Судья с рубрикой и вердиктом из закрытого списка (Python, Anthropic SDK 1.11, сверено с документацией 2026-10-02 — проверь у себя):

```python
from typing import Literal

import anthropic
from pydantic import BaseModel, ValidationError

client = anthropic.Anthropic()

RUBRIC = (
    "Ты проверяешь ответ бота поддержки по источнику. "
    "unknown: источник пуст или оборван. Иначе "
    "yes: каждое утверждение ответа есть в источнике, "
    "no: хотя бы одного утверждения в источнике нет. "
    "В поле why объясни вердикт одной фразой."
)


class Verdict(BaseModel):
    verdict: Literal["yes", "no", "unknown"]
    why: str


def judge(source, reply):
    content = (
        f"<source>{source}</source>\n"
        f"<reply>{reply}</reply>"
    )
    try:
        resp = client.messages.parse(
            model="claude-opus-5-5",
            max_tokens=2048,
            system=RUBRIC,
            output_format=Verdict,
            messages=[{"role": "user", "content": content}],
        )
    except ValidationError:
        return None
    return resp.parsed_output


v = judge(
    "Возврат в течение 14 дней по чеку.",
    "Вернуть товар можно в течение 30 дней.",
)
print(v.verdict if v else "нет вердикта")
```

Форму вердикта держит схема, которую `parse()` строит из класса `Verdict`. Отказ, обрыв по `max_tokens` и ответ не по схеме функция сводит к `None`: вердикта нет, и такой пример смотрят руками.

<Reveal q="Судья поставил ответам бота в среднем 4,8 из 5. Что нужно узнать о судье, прежде чем докладывать это число?">
Две вещи. По какой рубрике он судит: с одной строкой «оцени качество ответа» непонятно, за что ставится пятёрка. И как часто он согласен с человеком: судье дают ответы, которым человек уже вынес вердикт, и считают долю совпадений. Числу судьи верят после проверки самого судьи.
</Reveal>

<Callout type="blue" title="Насколько можно верить судье">
Сверку судьи с человеком называют **калибровкой**. В работе Zheng и соавторов (2023) GPT-4 в роли судьи выбирал лучший из двух ответов чат-ботов. С разметчиками-экспертами он соглашался в 85 % случаев, а они между собой — в 81 % (с ничьими — 66 и 63 %). Там же GPT-4 на десяти задачах по математике принял неверное решение за верное в 14 проверках из 20, а с собственным решением, полученным заранее отдельным запросом, — в 3. Это модели 2023 года, для моделей 2026 года таких замеров в уроке нет.
</Callout>

## Как на практике

- **Начни с 20–50 настоящих примеров.** Возьми то, что и так проверяешь руками перед выкаткой, и жалобы из поддержки. Дальше набор растёт: документация советует брать числом, пусть автоматическая проверка и грубее ручной.
- **Критерий запиши до прогона.** Сначала решают, что считать успехом, потом строят замер (так и в документации).
- **Клади в набор обе стороны.** Нужны случаи, где бот должен ответить, и случаи, где он должен отказаться или переспросить. В Anthropic на это наткнулись с веб-поиском: набор только из запросов, где искать надо, грозит агентом, который ищет почти по любому поводу.
- **Сравнивай на одном наборе.** До и после правки берутся те же примеры и те же критерии. Смотри общее число и список примеров, которые поменяли вердикт. Часть примеров держи в стороне от правок, как отложенный набор (held-out) в примере документации.
- **Читай провалы глазами.** Ошибиться могла проверка. В той же статье Opus 4.5 получил на CORE-Bench 42 %, пока исследователь не нашёл дефекты в самом наборе задач: проверка, например, браковала `96.12` при эталоне `96.124991…`. После исправлений и ослабления ограничений для модели вышло 95 %.
- **Записывай вместе с качеством токены и время.** Поле `usage` есть в каждом ответе, и прогон заодно покажет цену другой модели или более высокого effort.

Замер для задачи с эталоном помещается в один файл (Python, Anthropic SDK 1.11, сверено с документацией 2026-10-02 — проверь у себя):

```python
import anthropic

client = anthropic.Anthropic()

CASES = [
    {"text": "Доставили быстро, всё цело.",
     "label": "позитивный", "group": "простые"},
    {"text": "Обожаю ждать курьера по пять часов.",
     "label": "негативный", "group": "сарказм"},
    # … остальные примеры набора
]

OLD = (
    "Определи тональность отзыва. Ответь одним словом: "
    "позитивный, негативный или нейтральный."
)
NEW = OLD + " Сарказм считай негативным."


def answer(system, text):
    resp = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1024,
        system=system,
        messages=[{"role": "user", "content": text}],
    )
    return "".join(
        b.text for b in resp.content if b.type == "text"
    )


def run(system):
    verdicts = []
    for case in CASES:
        out = answer(system, case["text"])
        out = out.strip(" .!\n").lower()
        verdicts.append(out == case["label"])
    return verdicts


before, after = run(OLD), run(NEW)
print("до:", sum(before), "после:", sum(after))
for case, b, a in zip(CASES, before, after):
    if b != a:
        mark = "сломался" if b else "починился"
        print(mark, case["group"], case["text"])
```

Оба промпта требуют одно слово из списка, так что разницу между прогонами даёт новое правило, а формат ответа ни при чём. Последний цикл печатает примеры, которые поменяли вердикт.

## Три разбора

**Разбор 1. Общий балл вырос.**
Бот отвечает на вопросы по документации. Ты добавил в поиск новый источник и прогнал набор из ста вопросов: было 80 верных ответов, стало 84, и три прогона подряд дают 83–85. В наборе 80 простых вопросов и 20 сложных, где ответ собирается из нескольких разделов.

<Reveal q="Общий балл вырос на четыре пункта и держится от прогона к прогону. Выкатываешь?">
Нет. Четыре пункта на ста примерах укладываются в погрешность: по формуле из раздела про набор это 80 % плюс-минус 8 пунктов. Смотри группы. Простые: было 65 из 80, стало 79. Сложные: было 15 из 20, стало 5, и так в каждом из трёх прогонов. Это 75 и 25 % плюс-минус 19 пунктов, интервалы не пересекаются. Источник помог простым вопросам и сломал сложные, а общий балл это скрыл.
</Reveal>

Ход: прочитать сломанные сложные примеры и понять, чем им мешает новый источник. Вывод: общее число смотрят вместе с числами по группам.

**Разбор 2. Модель подешевле.**
Бот поддержки работает на дорогой модели, и ты хочешь перевести его на модель вдвое дешевле. Качество тут «мягкое», поэтому 50 типовых вопросов оценивает судья, отдельным запросом на каждое свойство: отвечает на вопрос, опирается на источник, вежлив. Сначала ты сверяешь судью с собой на двадцати ответах, и по опоре на источник вердикты совпадают в 19. По двум свойствам модели равны, а опора на источник упала с 47 до 41 из 50. Это 94 и 82 % с погрешностью 7 и 11 пунктов: интервалы пересекаются, да и судья расходится с тобой в одном ответе из двадцати. Ход: решение отложить, прогнать набор ещё дважды и добавить вопросов на опору на источник. Вывод: разницу в пределах погрешности проверяют новыми примерами и прогонами.

**Разбор 3. Где набор не нужен.**
Раз в квартал ты просишь модель набросать план отчёта и правишь его сам. Запрос не живёт в коде, промпт никто менять не собирается, каждый ответ читает человек. Набор здесь обойдётся дороже любой ошибки, которую он поймает. Вывод: замер окупается там, где запрос повторяется без тебя и систему собираются менять.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| Судить по трём ответам на глаз | Разброса и редких случаев в них не видно | Набор, критерий, число |
| Смотреть только общий балл | Он растёт, пока малая группа падает | Числа по группам |
| Верить судье без проверки | Судья сам ошибается, а размытая рубрика даёт размытый вердикт | Подробная рубрика и калибровка |
| Считать разницу в один-два примера улучшением | На малом наборе это может быть разброс | Повторные прогоны и список примеров, поменявших вердикт |
| Ставить `temperature=0`, чтобы замер повторялся | Полной повторяемости она не даёт; на Opus 5.5, Sonnet 5.5 и Fable 5.1 это ошибка 400, в Python SDK — `TypeError` (на 2026-10) | Повторные прогоны |

## Практикум

<Practice title="Собери мини-набор для своей системы" checklist={["В наборе 10–15 настоящих примеров, среди них крайние случаи и прошлые провалы", "Есть пример, где система должна отказаться или сказать «не знаю»", "У каждого примера записан критерий и чем его проверять: кодом или судьёй", "Для судьи есть рубрика с закрытым списком вердиктов и план калибровки", "Примеры разбиты на группы", "Записано, какую разницу ты считаешь улучшением, а какую разбросом"]}>
Возьми свою систему на LLM: промпт в коде, бота, поиск по базе. Если своей нет, возьми бота, который отвечает сотрудникам по внутренней документации.

1. Набери 10–15 примеров: вход и то, по чему судить ответ. Для упражнения хватит; рабочий набор начинают с 20–50 и растят. Добавь крайние случаи и то, на чём система уже ошибалась.
2. Каждому примеру запиши критерий и выбери, чем его проверять. Для судьи напиши рубрику.
3. Раздели примеры на группы.
4. Опиши, как сравнишь результат до и после правки и какую разницу сочтёшь улучшением.

<div slot="solution">
Пример для бота по документации. В наборе 12 вопросов: шесть простых, где ответ лежит в одном разделе, три сложных, где он собирается из двух, два прошлых провала и один вопрос без ответа в документации: на него бот должен сказать, что не знает.

Проверка смешанная. Где ответ — число или название, код ищет его в тексте. Остальное проверяет судья с рубрикой «каждое утверждение ответа есть в приложенном разделе: yes или no; unknown, если раздел пуст». Перед этим судья сверен с тобой на десяти старых ответах бота из лога.

В группах здесь от одного до шести примеров, проценты по ним ничего не скажут, поэтому по группам смотрим, какие примеры поменяли вердикт. Разница в один ответ из двенадцати может быть разбросом. Улучшением считается правка, после которой минимум два новых примера проходят в трёх прогонах подряд и ни один прошлый провал не вернулся.
</div>
</Practice>

<Callout type="teal" title="В работу">
Какой твой промпт или бот уже работает без замера? До пятницы выпиши для него десять настоящих запросов с ожидаемым результатом и прогони один раз: получится твоё число «до». Через неделю-две добавь в набор провалы, которые случились за это время, и прогони снова.
</Callout>

## Шпаргалка

| Что | Коротко |
| --- | --- |
| Замер (eval) | Набор примеров, критерий, прогон; на выходе число |
| Набор | Старт с 20–50 настоящих примеров: частые, крайние, прошлые провалы |
| Чем проверять | Сначала код: сверка с эталоном, разбор, запуск. Судья — когда кодом не выразить |
| LLM-судья | Подробная рубрика, закрытый список вердиктов, калибровка |
| До и после | Один набор, одни критерии, список примеров, поменявших вердикт |
| Группы | Число по каждой группе: общий балл скрывает падение малой |
| Разброс | Число меняется между прогонами; пока интервалы версий пересекаются, вывода нет |
| Провалы | Читать глазами: ошибиться могла проверка |
