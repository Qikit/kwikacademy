## Зачем это

В прошлом уроке ты решал, откуда взять инструмент: написать самому, включить готовый у вендора или подключить MCP-сервер. Теперь ассистенту нужны знания твоей компании. Сотрудник спрашивает: «Сколько дней отпуска переносится на следующий год?» Ответ лежит во внутренней вики, а модель её никогда не видела. В лучшем случае она скажет «не знаю», в худшем уверенно перескажет чужое правило.

Для таких вопросов есть **RAG**: перед ответом система находит в базе знаний, то есть в корпусе твоих документов, подходящие куски и кладёт их модели в контекст. Вокруг него два соблазна. Когда бот отвечает неверно, рука тянется поменять модель. А когда нужно, чтобы модель «знала наши документы», всплывает слово «дообучить»: продолжить её обучение на своих текстах. Оба хода стоят времени и денег, и оба могут оказаться мимо цели.

После урока ты сможешь спроектировать RAG для своей базы и выбрать между RAG, простым контекстом (база целиком в промпте) и дообучением.

## Ядро: найти нужное и подложить в контекст

<Callout type="purple" title="Суть">
**RAG** (Retrieval-Augmented Generation, генерация, дополненная поиском) состоит из двух шагов. На шаге **retrieval** (поиск) по вопросу пользователя достаёшь из своей базы несколько подходящих кусков. На шаге **generation** (генерация) кладёшь их в контекст и просишь модель ответить по ним. Знания остаются снаружи модели: изменился документ — обновляешь базу, модель не трогаешь.
</Callout>

Модель здесь работает читателем, которому приносят нужные страницы. Так устроен чат поддержки, который достаёт статьи из тысячи, и ассистент юриста, который находит пункты в архиве договоров. А договор, который ты сам вставил в чат, ещё не RAG. Опора на источник есть, ведь текст для ответа лежит в запросе, а шага поиска нет.

Что знания живут в базе, показала ещё работа 2020 года о RAG (Lewis и соавторы). Модель спрашивали о 82 мировых лидерах, сменившихся между 2016 и 2018 годами, и давали ей то Википедию 2018 года, то Википедию 2016-го. С новой базой она верно называла 68 % лидеров 2018 года, со старой 4 %. Саму модель не переобучали.

Прежде чем раскрыть ответ, ответь сам, хотя бы про себя.

<Reveal q="Бот по базе знаний ответил клиенту, что товар можно вернуть в течение 30 дней, а в регламенте написано 14. Что ты откроешь первым: настройки модели, промпт или куски, которые нашёл поиск?">
Куски. Если пункта про 14 дней среди них нет, модель его не видела и достроила ответ из выученных знаний, то есть из того, что вынесла из обучения. Ни модель сильнее, ни новый промпт нужного пункта в контекст не добавят. Если пункт на месте, а ответ с ним расходится, смотри на инструкцию и модель. Правило: разбор ошибки RAG начинают с выдачи поиска.
</Reveal>

## Как устроено: пайплайн из четырёх шагов

  { title: "Retrieval: найти куски", body: "Для вопроса пользователя считаешь вектор тем же эмбеддером и берёшь топ-k самых близких кусков. Если в вопросах бывают точные коды и артикулы, к семантическому поиску добавляют поиск по ключевым словам.", badge: "поиск" },
  { title: "Augmentation: собрать запрос", body: "Складываешь в один запрос найденные куски с названием и адресом источника, вопрос пользователя и инструкцию отвечать только по кускам. Английское слово значит «дополнение»: вопрос дополнен материалом для ответа.", badge: "сборка" },
  { title: "Generation: ответить по кускам", body: "Модель отвечает по тому, что лежит в контексте, и показывает, на какие куски опирается ответ. Пользователь может открыть источник и проверить.", badge: "ответ" }

Два шага из «Сути» здесь разложены на четыре: к поиску добавлена подготовка базы, к генерации — сборка запроса. Первые два знакомы по уроку про эмбеддинги, третий и четвёртый умещаются в один запрос к модели.

В Messages API для найденного куска есть свой тип блока, `search_result`: адрес источника, название и текст. Если включить цитирование, то, по документации, модель вернёт ответ частями, и к части, взятой из куска, будет приложена **цитата** (citation): адрес, название и текст этого куска. Вот запрос (Python, Anthropic SDK 1.11, сверено с документацией 2026-10-04 — проверь у себя). В `chunks` лежит то, что вернул твой поиск:

```python
import anthropic

client = anthropic.Anthropic()  # ключ из ANTHROPIC_API_KEY

question = "Сколько дней есть на возврат товара?"

# топ-k кусков, которые вернул твой поиск по базе
chunks = [
    {
        "source": "kb://returns/2",
        "title": "Возврат товара: сроки",
        "text": "Возврат принимается в течение 14 дней "
        "со дня получения заказа.",
    },
    {
        "source": "kb://delivery/5",
        "title": "Доставка: сроки",
        "text": "Курьер привозит заказ за 1–3 дня.",
    },
]

# augmentation: кусок становится блоком search_result
content = [
    {
        "type": "search_result",
        "source": c["source"],
        "title": c["title"],
        "content": [{"type": "text", "text": c["text"]}],
        "citations": {"enabled": True},
    }
    for c in chunks
]
# вопрос идёт после кусков, как в примере документации
content.append({"type": "text", "text": question})

# generation: ответ по кускам
resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    system=(
        "Отвечай только по найденным фрагментам. "
        "Если ответа в них нет, так и скажи."
    ),
    messages=[{"role": "user", "content": content}],
)

for block in resp.content:
    if block.type != "text":
        continue
    print(block.text)
    for cite in block.citations or []:
        print("  источник:", cite.title, cite.source)
        print("  цитата:", cite.cited_text)
```

Блоки ответа код перебирает по типу, потому что первым может прийти блок рассуждения, и `resp.content[0].text` на нём упадёт. Блок ответа с цитатой по документации (это форма, вывода модели здесь нет):

```json
{
  "type": "text",
  "text": "…",
  "citations": [
    {
      "type": "search_result_location",
      "cited_text": "текст процитированного блока",
      "source": "kb://returns/2",
      "title": "Возврат товара: сроки",
      "search_result_index": 0,
      "start_block_index": 0,
      "end_block_index": 1
    }
  ]
}
```

Со структурированным выводом цитирование не сочетается: запрос с цитатами и `output_config.format` вернёт ошибку 400.

<Reveal q="В ответе бота стоит фраза «по статье „Возврат товара“ срок 30 дней», но цитаты из API к ней нет. Можно ли считать, что факт взят из статьи?">
Нет. Название статьи в тексте написала сама модель, и проверки за ним нет. Цитату собирает API: по документации она всегда указывает на кусок из запроса и несёт его текст. Больше она ничего не гарантирует. Совпадает ли фраза ответа с куском, видно из сравнения с `cited_text`. Правило: цитата показывает, с чем сверять, а сверяешь ты.
</Reveal>

<Callout type="blue" title="Поиск можно отдать модели инструментом">
Поиск по базе можно объявить **инструментом**, как в уроке про инструменты: модель сама решит, идти ли в базу и с каким запросом, а твой код вернёт найденное теми же блоками `search_result` внутри `tool_result`. Отсюда один шаг до агентов, о них отдельный урок.
</Callout>

## Как устроено: два места отказа

Ошибается RAG в двух местах, и чинят их по-разному. Когда нужного куска нет среди найденных, это **промах поиска**: верно ответить модель не может. Второе место — генерация.

| В логах | Где сломалось | Что чинить |
| --- | --- | --- |
| Нужного куска нет среди найденных | Поиск (retrieval) | Нарезку, поиск, число кусков |
| Кусок найден, ответ с ним расходится | Генерация (generation) | Инструкцию, потом модель |
| Ответа нет в самой базе | Нигде: это пробел в базе | Дописать документ; «не знаю» здесь верный ответ бота |

<Reveal q="В опыте 2023 года моделям давали по 20 найденных документов, а потом по 50, и нужный документ стал попадать в выдачу чаще. Как думаешь, насколько выросла точность ответов?">
Примерно на 1–1,5 %, а запрос стал заметно длиннее (Liu и соавторы, модели того года). Нужный кусок должен попасть в контекст, но лишний текст отвлекает модель и стоит денег. Anthropic в 2024 году выбрала 20 кусков из 5, 10 и 20, но мерила другое: как часто нужный кусок в выдачу не попадает. Правило: число кусков подбирают по ответам на своих вопросах.
</Reveal>

## Как на практике

- **Пиши в лог найденные куски.** Без них промах поиска не отличить от промаха генерации. Собери пару десятков настоящих вопросов с известным куском-ответом и считай, как часто он попадает в выдачу. Число кусков выбирай по ответам на тех же вопросах.
- **Запрети отвечать мимо кусков и разреши «не знаю».** Это делает инструкция в `system` из примера. По документации Anthropic, разрешение признать незнание резко сокращает ложные сведения. Там же оговорка: приёмы уменьшают галлюцинации, но не убирают их.
- **Показывай источник цитатой.** Выводи пользователю название и адрес из цитаты. Цитируется блок текста целиком. Нужна ссылка точнее — раздели текст куска на несколько блоков в `content`.
- **Обновляй индекс вместе с документами.** Изменился регламент — пересчитай векторы его кусков. Старую версию бот перескажет так же уверенно, как новую.

## Три разбора

**Разбор 1. Чат по базе поддержки.**
В базе тысяча статей, клиенты спрашивают своими словами. Дообучать модель на статьях незачем. Их правят каждую неделю, а клиенту нужна ссылка для проверки. Ход: поиск достаёт двадцать ближайших кусков, в запрос они уходят блоками `search_result`, в `system` стоит «отвечай только по найденным фрагментам». Рядом с утверждениями, взятыми из кусков, пользователь видит ссылку на статью. Вывод: знания, которые меняются и требуют проверки, держат в базе и подают модели по запросу.

**Разбор 2. Плохой поиск — плохой ответ.**
Бот по регламентам уверенно назвал срок согласования договора, но срок оказался от другого типа договора. Команда уже обсуждает модель подороже. В логе видно другое: поиск вернул куски из соседнего раздела, нужного пункта среди них нет. Регламент резали по несколько страниц на кусок, а в векторе большого куска отдельный пункт может потеряться. Ход: резать по пунктам, пересчитать индекс и проверить на вопросах из истории, что нужный пункт попадает в выдачу. Вывод: когда нужного куска нет в контексте, чинят нарезку и поиск, смена модели не поможет.

**Разбор 3. Где RAG лишний.**
У тебя один договор на сорок страниц и три вопроса по нему. Нарезка, эмбеддер и векторная база здесь лишние, потому что договор целиком помещается в контекст-окно. Ход: положить текст в запрос, вопрос поставить после него и попросить сначала выписать цитаты, как в уроке про контекст-окно. Вывод: RAG окупается, когда база большая, меняется или не помещается в один запрос.

## RAG, контекст или дообучение

Сначала предскажи. В работе 2024 года (Ovadia и соавторы, EMNLP) трём открытым моделям размера 7B задавали вопросы с четырьмя вариантами ответа о событиях, которые случились после их обучения. Статьи об этих событиях модели получали двумя путями: через RAG или дообучением на сыром тексте тех же статей.

<Reveal q="Без помощи Mistral 7B отвечала верно на 48,1 % вопросов. Как думаешь, сколько стало после дообучения и сколько с RAG?">
После дообучения 50,4 %, с RAG 87,5 %. Одной из трёх моделей дообучение результат даже ухудшило. Авторы предполагают, что новый факт модель усваивает, только когда он встречается ей при обучении во многих формулировках. Они же оговаривают, что вопросы составляли по статьям из базы и RAG это помогло. Правило: новые факты кладут в базу, а не в веса.
</Reveal>

О первой развилке Anthropic писала в сентябре 2024 года: базу меньше 200 тысяч токенов, около 500 страниц, можно положить в промпт целиком и обойтись без RAG. Страницы там английские и посчитаны прежним токенизатором: у Opus 5.5 они займут примерно 270 тысяч токенов. Окно у Opus 5.5, Sonnet 5.5 и Fable 5.1 на 2026-10 — миллион токенов. Но «помещается» не значит «выгодно». 200 тысяч входных токенов у Opus 5.5 стоят 80 центов на каждый вопрос, а с ростом контекста, по словам Anthropic, падает точность. При частых вопросах цену сбивает кэш промпта, о нём урок про продакшн.

Вторую и третью развилки руководство OpenAI разводит по двум осям: модели не хватает знаний или она нестабильно себя ведёт. **Дообучение** (fine-tuning) продолжает обучение готовой модели на твоих данных и меняет поведение. Так получают маленькую модель, натасканную на одну задачу, или тон, который не удержали ни инструкция, ни примеры. А регламент, загруженный в базу RAG, — не дообучение, ведь веса модели не изменились.

Для фактов дообучение подходит плохо. Знания в весах не поправить без нового обучения, и по ответу не видно, откуда взят факт. Базу RAG, как писали ещё Lewis и соавторы, можно править и просматривать. Поведение сначала чинят промптом, примерами и схемой вывода: это дешевле проверить. К тому же в Claude API дообучения нет, а OpenAI свою платформу дообучения сворачивает (на 2026-10). В этом курсе дообучение не разбирается.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| Менять модель, не открыв выдачу поиска | Без нужного куска внутренний факт не назовёт ни одна модель | Сначала посмотреть найденные куски |
| Не писать «отвечай только по фрагментам» | Модель может достроить ответ из выученных знаний | Инструкция и разрешение сказать «не знаю» |
| Дообучать модель ради фактов | Факты в весах не поправить без нового обучения и не проверить по источнику | Факты держать в базе RAG |
| Верить названию источника в тексте ответа | Его написала модель, проверки за ним нет | Цитата из API и сверка фразы с её текстом |
| Строить RAG для базы, которая помещается в окно | Лишняя система там, где хватит одного запроса | Положить базу в промпт и посчитать цену |

1. Сколько в базе токенов, помещается ли она в окно и во что обойдётся класть её в каждый запрос?
2. Как режешь корпус, чем ищешь и сколько кусков кладёшь в запрос?
3. Из чего соберёшь запрос и что ответит бот, если в кусках ответа нет?
4. Как пользователь увидит источник?
5. Как проверишь поиск и что откроешь первым, когда бот ошибётся?
6. Что в задаче относится к тону ответа и чем ты это закроешь?

<div slot="solution">
Пример. База — документация продукта на английском, около трёх тысяч страниц, правки каждую неделю. При 300 словах на странице это 900 тысяч слов, для Opus 5.5 примерно 1,6 млн токенов (1,8 токена на слово). В окно база не помещается, да и миллион входных токенов стоил бы 4 доллара за вопрос. Нужен RAG. Русскую базу так не прикинешь, её считают `count_tokens`.

Режем по подзаголовкам, эмбеддер `voyage-4`: кускам `input_type="document"`, вопросам `"query"`. В запрос идут двадцать кусков блоками `search_result` с цитатами, вопрос после них, в `system` стоит инструкция из примера. Пользователь видит название страницы и адрес из цитаты.

Для замера берём тридцать вопросов из рабочего чата с известной страницей-ответом. Считаем, как часто она попадает в выдачу, и сравниваем ответы при 5, 10 и 20 кусках. Бот ошибся — первым открываем лог найденных кусков. Тон («коротко, без канцелярита») задаём инструкцией в `system`, дообучение не нужно.
</div>
</Practice>

<Callout type="teal" title="В работу">
Где в твоей работе люди раз за разом задают вопросы по одним и тем же документам? До пятницы выпиши десять таких вопросов и рядом с каждым документ с ответом: это готовый набор для замера поиска. Через неделю-две проверь, не изменились ли ответы вместе с документами.
</Callout>

## Шпаргалка

| Что | Коротко |
| --- | --- |
| RAG | Retrieval (найти куски) и generation (ответить по ним) |
| Запрос | Блоки `search_result`, после них вопрос; `citations: {"enabled": True}` |
| Инструкция | «Только по найденным фрагментам; нет ответа — так и скажи» |
| Источник | Цитата из API: `source`, `title`, `cited_text`; фразу сверяй с текстом |
| Ответ неверный | Сначала выдача поиска, потом инструкция и модель |
| Число кусков | По ответам на своих вопросах |
| База помещается в окно | Простой контекст; посчитай токены и цену запроса |
| Дообучение | Меняет поведение, для фактов подходит плохо; в Claude API нет (2026-10) |

## Источники

- **Lewis и соавторы — Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks (NeurIPS 2020)** ([arxiv.org](https://arxiv.org/abs/2005.11401)) — внешняя база вместо знаний в весах, опыт с подменой базы.
- **Anthropic — Search results, Citations, Glossary, Reduce hallucinations, Context windows, Pricing** ([platform.claude.com/docs](https://platform.claude.com/docs/en/build-with-claude/search-results), сверено 2026-10-04) — блок `search_result` и цитаты, определения RAG и дообучения, приёмы против галлюцинаций, окно и цена.
- **Anthropic — Introducing Contextual Retrieval, 2024** ([anthropic.com](https://www.anthropic.com/engineering/contextual-retrieval), сверено 2026-10-04) — порог в 200 тысяч токенов, сравнение 5, 10 и 20 кусков.
- **OpenAI — Optimizing LLM Accuracy, Model optimization** ([developers.openai.com](https://developers.openai.com/api/docs/guides/optimizing-llm-accuracy), сверено 2026-10-04) — знания и поведение как разные оси, сворачивание дообучения.
- **Ovadia и соавторы — Fine-Tuning or Retrieval? Comparing Knowledge Injection in LLMs (EMNLP 2024)** ([aclanthology.org](https://aclanthology.org/2024.emnlp-main.15/), сверено 2026-10-04) — дообучение против RAG, таблица 2.
- **Liu и соавторы — Lost in the Middle: How Language Models Use Long Contexts (TACL, т. 12, 2024)** ([arxiv.org](https://arxiv.org/abs/2307.03172)) — от 20 к 50 документам точность почти не растёт.
