## Зачем это

Модель не знает твоих данных. Внутренняя вики, свежие документы, приватная база клиентов — ничего этого нет в её весах: часть появилась после обучения (knowledge cutoff), часть закрыта. Спросишь «что у нас записано по проекту X» — в лучшем случае честное «не знаю», в худшем — уверенный вымысел (мы это разбирали в уроке про границы).

Запихнуть всю базу в каждый запрос не выйдет: не влезет в окно и разорит на токенах. Нужен способ подкладывать модели **только относящиеся к вопросу** куски знаний. Это и есть RAG — приём, на котором стоит большинство корпоративных LLM-систем: чат по документации, ассистент по внутренней базе, поиск-с-ответом.

К этому моменту ты будешь понимать, из чего состоит RAG (retrieval + generation) и почему его качество упирается в поиск, а не в модель, — и сможешь выбрать между RAG, простым контекстом и дообучением под конкретную задачу.

## Ядро: найти нужное и подложить в контекст

<Callout type="purple" title="Суть">
**RAG** (Retrieval-Augmented Generation) — это два шага. Сначала **retrieval**: по вопросу пользователя семантическим поиском достаёшь из своей базы несколько релевантных кусков (тем самым поиском по эмбеддингам из прошлых уроков). Затем **generation**: кладёшь эти куски в контекст модели и просишь ответить, **опираясь на них**. Модель отвечает по подложенным фактам, а не по памяти. База знаний остаётся снаружи модели — обновляешь её, не трогая и не переобучая саму модель.
</Callout>

Устроено это так: знания живут не в модели, а рядом с ней. Модель здесь — не источник фактов, а «читатель», который берёт поданные ему куски и складывает из них ответ. Поменялись документы — поменял базу; модель осталась прежней. Это и делает RAG таким практичным: свежесть и приватность данных — вопрос твоей базы, а не переобучения модели.

<Reveal q="RAG отвечает неверно. Чинить надо модель?">
Чаще всего — нет. Первым делом смотри на retrieval: **что** нашёл поиск и **те ли** это куски. Если подложили нерелевантные фрагменты, даже идеальная модель ответит мимо — garbage in, garbage out. Проблема RAG почти всегда в поиске, а не в генерации.
</Reveal>

## Как устроено: пайплайн из четырёх шагов

<StepThrough caption="Путь вопроса через RAG" steps={[

  { title: "Retrieval — найти релевантное", body: "Вопрос пользователя эмбеддишь тем же эмбеддером и ищешь в базе топ-k ближайших по смыслу кусков. Именно здесь семантический поиск находит нужное, даже если слова в вопросе и в документе разные.", badge: "поиск" },
  { title: "Augmentation — собрать промпт", body: "Складываешь промпт: инструкция «ответь, опираясь только на приведённые фрагменты», сами найденные куски и вопрос пользователя. Модель получает и вопрос, и материал для ответа в одном контексте.", badge: "сборка" },
  { title: "Generation — ответ по фактам", body: "Модель отвечает, опираясь на подложенные куски, а не на память. Хорошая практика — просить её ссылаться на источник, чтобы ответ можно было проверить.", badge: "ответ" }
]} />

Шаги augmentation и generation — самая код-осязаемая часть RAG: собрать промпт из найденных кусков и получить ответ по ним. Вот как (Python, Anthropic SDK, актуально на 2026-07 — проверь у себя; `chunks` — топ-k, что вернул семантический поиск из урока про эмбеддинги):

```python
# augmentation: собираем контекст из найденных кусков
context = "\n\n".join(f"[Источник {i + 1}] {c}" for i, c in enumerate(chunks))

# generation: инструкция «только по контексту» + куски + вопрос
resp = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=1024,
    system=(
        "Отвечай на вопрос, опираясь ТОЛЬКО на приведённые фрагменты. "
        "Если ответа в них нет — так и скажи. Указывай номер источника."
    ),
    messages=[{"role": "user", "content": f"{context}\n\nВопрос: {question}"}],
)
```

Инструкция «только по контексту» в `system` — тот самый приём против галлюцинаций (ниже), а нумерация источников даёт проверяемость. Retrieval (получение `chunks`) остаётся за семантическим поиском — здесь показан именно мост от найденных кусков к ответу.

<Callout type="blue" title="Retrieval можно оформить как инструмент">
Поиск по базе необязательно делать до вызова модели — его можно дать модели **инструментом** (из прошлого урока): тогда модель сама решает, когда сходить в базу, и с каким запросом. Это шаг в сторону агентов — модель не просто получает готовые куски, а управляет поиском. Механика та же: retrieval достаёт факты, generation складывает из них ответ.
</Callout>

## Как на практике

**Качество RAG = качество retrieval.** Это главное. Модель не выдумает хороший ответ из плохих кусков. Если ответы мимо — проверяй сначала, что находит поиск: релевантны ли куски, не мешает ли нарезка, тот ли эмбеддер.

**Проси отвечать только по контексту.** Явная инструкция «опирайся только на приведённые фрагменты, если ответа в них нет — так и скажи» резко снижает галлюцинации: модель перестаёт дополнять факты из памяти. Без неё она склонна «дописать» недостающее.

**Показывай источники.** Ответ со ссылкой на конкретный документ можно проверить; ответ без источника — нет. Проверяемость — то, ради чего RAG во многом и затевают.

**Следи за числом и размером кусков.** Мало кусков — не хватит контекста для ответа; слишком много — модель тонет в шуме, а запрос дорожает. Баланс подбирают под корпус, но обе крайности вредят.

## RAG, контекст или дообучение

Три способа «дать модели то, чего она не знает», под разные задачи. Пройди по вопросам сверху вниз:

<DecisionTree nodes={[
  { q: "Данных мало и они влезают в окно — и это разовый вопрос?", yes: "просто положи их прямо в промпт (контекст), RAG не нужен", no: "смотри дальше" },
  { q: "Нужны свежие, приватные или объёмные знания (факты), которых нет в модели?", yes: "RAG: retrieval нужных кусков + generation по ним", no: "смотри дальше" },
  { q: "Нужно изменить стиль, формат или поведение модели, а не дать ей факты?", yes: "дообучение (fine-tune) — оно про поведение, не про знания", no: "вернись к контексту или RAG" }
]} />

Ключевая развилка, которую путают чаще всего: **RAG — про знания, fine-tune — про поведение.** Дообучение не лучший способ «вложить факты»: оно дорого, факты в нём устаревают и проверить их нельзя. Хочешь, чтобы модель знала твои документы, — это RAG. Хочешь, чтобы она всегда отвечала в определённом формате или тоне, — это fine-tune.

## Три разбора

**Разбор 1. Чат по базе поддержки.**
База из 1000 статей, пользователь спрашивает своими словами. Retrieval достаёт топ-3 релевантные статьи, augmentation кладёт их в промпт с инструкцией «отвечай по ним и ссылайся на статью», модель отвечает с указанием источника. Fine-tune тут не нужен — это чистая работа со знаниями, а знания лучше держать в обновляемой базе, а не в весах.

**Разбор 2. Плохой retrieval — плохой ответ.**
RAG-бот уверенно ответил неправильно. Разбираешь: retrieval подложил не те куски — нарезка была слишком крупной, и в топ-k попал фрагмент про соседнюю тему. Модель добросовестно ответила по тому, что дали. Вывод: чинить надо не модель и не промпт генерации, а retrieval — нарезку и поиск. Это самая частая точка отказа RAG.

**Разбор 3. Когда RAG избыточен.**
Есть один короткий документ на пару страниц, и нужно разово ответить на вопрос по нему. Разворачивать эмбеддинги, векторную базу и retrieval здесь — избыточно: документ целиком влезает в контекст-окно. Просто положи его в промпт с вопросом. RAG оправдан, когда данных много, они меняются или их нельзя держать в одном запросе, — а не всегда, когда «данные снаружи модели».

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| Винить модель за плохой ответ RAG | Причина почти всегда в retrieval | Сначала проверить, что и то ли нашёл поиск |
| Не просить «отвечай только по контексту» | Модель дополняет факты из памяти | Явная инструкция + «нет ответа — так и скажи» |
| Дообучать модель ради фактов | Дорого, устаревает, не проверить | Знания — в RAG, fine-tune — для поведения |
| Крупная или кривая нарезка корпуса | В топ-k попадает нерелевантное | Резать по смысловому блоку, проверять retrieval |
| Не показывать источники | Ответ нельзя проверить | Ссылаться на конкретный документ |
| Класть слишком много кусков | Шум в контексте и рост цены | Держать топ-k небольшим и релевантным |

3. Как покажешь пользователю источник, чтобы ответ можно было проверить?

Пример. База — внутренняя вики, режем по подзаголовкам. На вопрос эмбеддим запрос, достаём топ-3 раздела, собираем промпт: «Ответь на вопрос, опираясь только на приведённые разделы; если ответа в них нет — скажи об этом. [разделы] Вопрос: …». В ответе просим модель указать заголовок раздела-источника. Проверка на избыточность: если вся вики — это одна страница на экран, RAG не нужен, кладём её целиком. RAG оправдан именно объёмом и изменчивостью базы, а не самим фактом, что данные снаружи модели.

## Шпаргалка

| Что | Коротко |
| --- | --- |
| RAG | Retrieval (найти куски) + Generation (ответить по ним) |
| Знания | Снаружи модели, в обновляемой базе |
| Retrieval | Семантический поиск топ-k по эмбеддингам |
| Качество RAG | Упирается в retrieval, не в модель |
| Против галлюцинаций | «Отвечай только по контексту, нет — скажи» |
| Проверяемость | Показывать источник ответа |
| RAG vs fine-tune | Знания vs поведение/стиль |
| Когда не нужен | Мало данных, влезают в окно, разово |
