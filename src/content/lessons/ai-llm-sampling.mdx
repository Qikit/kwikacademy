## Зачем это

Задаёшь модели один и тот же вопрос дважды — и получаешь два разных ответа. Для чата это приятно (живее), для кода, который парсит вывод, — катастрофа: вчера работало, сегодня сломалось, промпт не менялся. Причина не в баге и не в «настроении» модели, а в одном параметре, который по умолчанию стоит так, что ответы гуляют.

Понять семплинг — значит получить руль: где нужен один и тот же ответ на один и тот же вход, а где, наоборот, десять разных идей. Без этого ты то дерёшься с недетерминизмом там, где хотел стабильности, то получаешь скучные однообразные варианты там, где просил разнообразия.

Когда дочитаешь, ты будешь понимать, что модель выдаёт распределение вероятностей и как из него выбирается токен, — и сможешь осознанно ставить детерминизм под задачу.

## Ядро: модель даёт распределение, семплинг выбирает

<Callout type="purple" title="Суть">
На каждом шаге модель выдаёт не один токен, а **распределение вероятностей** по всему словарю: «Париж» — 0.92, «город» — 0.03, и так далее. Что делать с этим распределением — решает **семплинг**. Можно всегда брать самый вероятный токен (детерминированно), можно тянуть случайно с учётом вероятностей (разнообразно). **Температура** — ручка между этими режимами. Отсюда и разные ответы на один промпт: не модель «передумала», а семплинг вытянул другой токен.
</Callout>

Вспомни прошлые уроки: модель предсказывает следующий токен *по вероятности*. Ключевое слово — вероятность: на выходе не выбор, а распределение. Сам «выбор» происходит уже после модели, на этапе семплинга, и им можно управлять, не трогая ни веса, ни промпт.

<Reveal q="Температура 0 — ответ будет абсолютно одинаковым каждый раз?">
Почти. При температуре 0 семплинг всегда берёт самый вероятный токен, так что ответ становится практически стабильным. Но абсолютной гарантии нет: на уровне железа (порядок операций с плавающей точкой, батчинг запросов на сервере) возможны редкие расхождения. Практический вывод: 0 даёт воспроизводимость «почти всегда», а не математическую гарантию, — для критичных проверок это стоит держать в голове.
</Reveal>

## Как устроено: температура крутит «остроту» распределения

Температура меняет форму распределения перед выбором:

- **Низкая (→ 0):** распределение заостряется, вероятность лидера растёт почти до единицы. Семплинг почти всегда берёт самый вероятный токен — это близко к **жадному** выбору (greedy). Ответы стабильные, предсказуемые.
- **Высокая (→ 2):** распределение сглаживается, у аутсайдеров появляется реальный шанс. Семплинг чаще тянет неожиданные токены — ответы разнообразнее, но выше риск бессвязицы.

  { upTo: 2.0, title: "Хаотично и креативно", text: "Модель чаще выбирает маловероятные токены. Брейнсторм, необычные варианты — но заметно выше риск бессвязного вывода." }
]} />

Рядом с температурой часто идёт **top-p** (nucleus sampling): вместо всего словаря семплинг берёт только самые вероятные токены, набирающие в сумме долю *p* (например, 0.9), и тянет из них. Есть и **top-k** (только k лидеров). Идея одна — ограничить, из чего выбирать; на практике температуру трогают чаще, а top-p оставляют по умолчанию.

<Callout type="blue" title="Где найти эту ручку — и где её уже нет">
Температура — параметр запроса к API (`temperature`), обычно от 0 до 1–2 в зависимости от вендора. Важная оговорка на 2026-07: у новейших reasoning-моделей Claude (Opus 4.8, Sonnet 5, Fable 5) `temperature` и `top_p` **убраны** — глубину и режим ответа там задаёт механизм рассуждения (thinking / effort), а не температура. На более простых моделях и у других вендоров параметр на месте. Вывод: сам приём семплинга универсален, но доступность ручки зависит от модели — сверяйся с докой конкретной модели, а не с общим правилом.
</Callout>

## Как на практике: детерминизм под задачу

Правило простое — **чем важнее стабильность и точность, тем ниже температура; чем важнее разнообразие, тем выше.**

- **Низкая (0–0.3):** извлечение данных, классификация, код, структурированный вывод, фактические ответы. Всё, где «правильный ответ один» и его надо воспроизводимо получать.
- **Средняя (0.4–1.0):** обычный диалог, объяснения, черновики текста — живо, но связно.
- **Высокая (1.0+):** брейнсторм, генерация вариантов названий, творческие тексты — когда разнообразие ценнее предсказуемости.

Вот как параметр выглядит в запросе (Python, Anthropic Messages API, 2026-07 — доступность зависит от модели, см. оговорку выше; проверь у себя):

```python
from anthropic import Anthropic

client = Anthropic()

resp = client.messages.create(
    model="claude-haiku-4-5",
    max_tokens=512,
    temperature=0.0,  # 0 — детерминированнее (для извлечения/кода); выше — разнообразнее
    messages=[{"role": "user", "content": "Верни JSON с полями name и email из текста ниже: ..."}],
)
print(resp.content[0].text)
```

Для извлечения полей ставим `temperature=0.0`: нам нужен один и тот же разбор одного и того же текста, а не десять вариантов. Для генерации идей — подняли бы к 1.0+.

## Три разбора

**Разбор 1. Стабильный JSON на температуре 0.**
Тебе нужно из письма вытащить сумму и дату в JSON, и код это парсит. На температуре 0 модель на один и тот же текст даёт один и тот же разбор — парсер спокоен. Подними температуру — и та же задача начнёт иногда менять формулировки, порядок полей, добавлять «пояснения», ломая парсинг. Для машиночитаемого вывода детерминизм не роскошь, а требование.

**Разбор 2. Брейнсторм на высокой.**
Просишь двадцать названий для сервиса. На температуре 0 модель выдаст двадцать почти одинаковых, вылизанных, скучных вариантов — она же каждый раз берёт «самое вероятное». Поднимаешь к 1.2 — и получаешь настоящий разброс, где половина мимо, но пара идей неожиданно хороши. Здесь разнообразие и есть цель, а редкие токены — это фича, не баг.

**Разбор 3. Тест, который падает через раз.**
Ты написал проверку: «модель на этот вход должна вернуть вот такой ответ». Иногда зелёная, иногда красная, код не менялся. Причина — температура по умолчанию не ноль, ответ каждый раз чуть другой, и точное сравнение то совпадает, то нет. Лечение: для детерминированных проверок ставь температуру 0 (и помни про остаточный недетерминизм железа — сравнивай по сути, а не по символу, где можно).

## Детерминизм и разнообразие — компромисс, а не «настройка получше»

Нет «правильной» температуры вообще — есть правильная под конкретную задачу. Один и тот же дефолт для парсинга JSON и для генерации идей будет плох в обоих случаях по-разному.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| Дефолтная температура для стабильных задач | Вывод гуляет, парсер и тесты ломаются | Температура 0 для кода/извлечения/схемы |
| Ждать полного детерминизма от LLM | Даже при 0 бывает остаточный разброс (железо) | Сравнивать по сути; не строить на побайтовом совпадении |
| Крутить температуру вместо промпта | Разнообразие ≠ качество; суть не улучшится | Сначала чинить промпт, температура — тонкая доводка |
| Высокая температура для фактов | Растёт шанс уверенной выдумки | Низкая температура + проверка/источник |
| Трогать top-p и top-k без нужды | Лишние ручки, непредсказуемый эффект | Обычно менять только температуру |
| Считать параметр универсальным | На новейших моделях его может не быть | Сверять доку конкретной модели |

1. Извлечь ИНН и сумму из счёта в JSON.
2. Придумать слоганы для рекламной кампании.
3. Классифицировать отзыв как «позитивный / негативный / нейтральный».

5. Сгенерировать тестовые данные с разнообразными вариантами.

- **2 и 5 — высокая (1.0–1.4).** Слоганы и разнообразные тестовые данные: разнообразие и есть цель, редкие токены дают неожиданные удачные варианты.

Где критичен недетерминизм: задачи 1 и 3, если их вывод парсит код или по нему принимается решение. И помни: если работаешь с моделью, где `temperature` недоступен, стабильность придётся закладывать иначе (промпт, схема вывода, валидация) — это следующие уроки.

## Шпаргалка

| Что | Коротко |
| --- | --- |
| Что выдаёт модель | Распределение вероятностей по токенам, не один ответ |
| Семплинг | Как из распределения выбирается токен |
| Температура | Ручка «остроты»: 0 — детерминированно, выше — разнообразно |
| Greedy (жадный) | Всегда самый вероятный токен (≈ температура 0) |
| top-p / top-k | Ограничить пул токенов для выбора; обычно не трогают |
| Низкая температура | Код, извлечение, классификация, факты |
| Высокая температура | Брейнсторм, варианты, творчество |
| Недетерминизм | Даже при 0 бывает остаточный разброс (железо) |
| Доступность | На новейших reasoning-моделях Claude параметра может не быть |
