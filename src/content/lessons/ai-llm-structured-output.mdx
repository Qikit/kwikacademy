## Зачем это

В прошлом уроке ты выбирал, насколько глубоко модели думать, и задавал это параметром effort. Форму ответа он не задаёт, а она нужна, когда ответ читает код. В демо ты просишь «верни JSON с полями name и email», и код разбирает ответ. На сотом запросе в проде модель начинает с «Конечно! Вот результат:», и **парсер**, то есть код, который превращает текст в объект, падает на первом символе.

Модель при этом не сломалась. «Верни JSON» было просьбой, и модель выполняла её, пока это было самым правдоподобным продолжением. Отсюда первое заблуждение: «хорошо попрошу, и будет надёжно». Второе появляется, когда форму уже держит механизм: «раз JSON прошёл схему, данным можно верить». Первое заблуждение время от времени роняет парсер. Второе тихо кладёт в базу сумму, которой в письме не было.

После урока ты сможешь получить от модели JSON, который гарантированно соответствует схеме, и обработать случаи, когда гарантия не действует.

## Ядро: структура как контракт, а не просьба

<Callout type="purple" title="Суть">
Когда ответ модели читает код, форму должен держать механизм. Его даёт **структурированный вывод (structured outputs)**. Ты передаёшь в запросе **JSON-схему**, и API ограничивает генерацию, чтобы ответ ей соответствовал. Гарантия покрывает только **форму**, то есть поля и типы. Верны ли значения, не отказалась ли модель отвечать и не оборвался ли ответ на лимите токенов, проверяет твой код.
</Callout>

За просьбу отвечает модель, и выполняет она её с какой-то вероятностью. По документации Anthropic, без структурированного вывода даже при аккуратном промпте встречаются битый синтаксис, пропущенные обязательные поля и не те типы. За схему отвечает API, и токен, который сломал бы форму, модель выбрать не может.

Прежде чем раскрыть ответ, ответь сам, хотя бы про себя.

<Reveal q="Модель пишет письмо клиенту и заодно ставит заявке срочность, по которой код выбирает очередь. Нужна ли схема ради одного слова?">
Нужна. Длина тут ни при чём. Код ждёт одно из заранее известных значений, а в свободном тексте модель напишет «высокая», «Срочно!» или целую фразу, и ветка в коде не сработает. Схема нужна, как только хотя бы одно значение читает программа.
</Reveal>

## Как устроено: схема в запросе

**JSON-схема (JSON Schema)** — это та самая схема вывода из урока про семплинг. Она описывает форму данных ключевыми словами: какие поля есть у объекта, какого они типа, какие обязательны. Схема контакта требует два обязательных строковых поля, `name` и `email`. В схеме для разбора отзывов у поля `sentiment` три допустимых значения, их перечисляет ключевое слово **`enum`**. А вот образец JSON, вставленный в промпт, схемой не станет. Модель его увидит, но повторять не обязана.

Схему передают в параметре `output_config`, в поле `format`. В прошлом уроке в этом же параметре лежал effort, так что он задаёт и глубину ответа, и его форму.

Запрос со схемой (Python, Anthropic SDK 1.11, сверено с документацией 2026-10-02 — проверь у себя):

```python
import json

import anthropic

client = anthropic.Anthropic()

SCHEMA = {
    "type": "object",
    "properties": {
        "name": {"type": "string"},
        "email": {"type": "string"},
    },
    "required": ["name", "email"],
    "additionalProperties": False,
}

resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=4096,
    output_config={
        "format": {"type": "json_schema", "schema": SCHEMA},
    },
    messages=[{
        "role": "user",
        "content": "Извлеки контакт: Иван Петров, "
                   "ivan@example.com",
    }],
)

if resp.stop_reason != "end_turn":
    raise RuntimeError(resp.stop_reason)

text = next(
    b.text for b in resp.content if b.type == "text"
)
contact = json.loads(text)
print(contact["name"], contact["email"])
```

Строку с `additionalProperties` API требует у каждого объекта схемы. На своей стороне он компилирует схему в **грамматику** — правила о том, какой токен допустим в каждой точке ответа. Из урока про семплинг ты помнишь, что модель выдаёт вероятности для всех токенов, а один из них выбирается отдельным шагом. Здесь на этом шаге остаются только токены, которые схему не нарушают. Приём называется **ограниченное декодирование (constrained decoding)**. Вступлению «Конечно! Вот результат:» взяться неоткуда: его первый токен грамматика не пропустит.

Старый совет «поставь температуру 0 ради стабильного JSON» формы не гарантирует, потому что температура меняет частоту маловероятных токенов, а о схеме ничего не знает.

В Python есть путь короче, метод `client.messages.parse()`, и Anthropic его рекомендует. Форму задаёшь классом **Pydantic**. Это библиотека, которая описывает данные классами Python и проверяет их. SDK превращает класс в схему, сам добавляет `additionalProperties`, отправляет схему в `output_config.format`, проверяет ответ и кладёт готовый объект в `parsed_output`. Тот же запрос через `parse()` (SDK 1.11, сверено 2026-10-02):

```python
from typing import Optional

import anthropic
from pydantic import BaseModel

client = anthropic.Anthropic()


class Contact(BaseModel):
    name: str
    email: Optional[str]


resp = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=4096,
    output_format=Contact,
    messages=[{
        "role": "user",
        "content": "Извлеки контакт: Иван Петров, "
                   "ivan@example.com",
    }],
)

contact = resp.parsed_output
if contact is None:
    raise RuntimeError(resp.stop_reason)
print(contact.name, contact.email)
```

Во втором примере `email` стал `Optional[str]`, а в первом был обязательной строкой. Причину попробуй предсказать сам.

<Reveal q="В первой схеме email — обязательная строка. Модели пришло письмо, в котором адреса нет. Как думаешь, что окажется в поле?">
Какая-то строка: пустая, «не указан» или адрес, которого в письме не было. Схема требует и поле, и тип, а сказать «адреса нет» модели нечем. Что именно она впишет, документация не обещает. С `Optional[str]` в схему попадает вариант `null`, и у модели появляется честный ответ.
</Reveal>

## Как устроено: где гарантия кончается

Обещано соответствие схеме, и не больше. Вот что остаётся за этой границей.

- **Смысл значений.** Схема знает, что `amount` должен быть числом. Было в письме 1500 или 15 000, она не знает.
- **Отказ.** Модель может отказаться отвечать по соображениям безопасности. Тогда в поле **`stop_reason`**, где записана причина остановки, стоит `refusal`, а содержимое ответа может не соответствовать схеме. Повторять тот же запрос нет смысла, потому что по документации та же модель обычно отказывает снова.
- **Обрыв.** Когда ответ упирается в `max_tokens`, в `stop_reason` стоит `max_tokens`, а JSON может оказаться неполным. Документация советует повторить запрос с большим лимитом.
- **Регистр в `enum`.** Значение может отличаться от записанного в схеме регистром букв, и ответ при этом завершится штатно. Такие значения сравнивай без учёта регистра.

К тому же API принимает не весь JSON Schema. На числовые границы вроде `minimum`, длину строк и рекурсию он ответит ошибкой 400. Метод `parse()` границу числа из класса переносит в описание поля и проверяет сам, на готовом ответе.

У этого удобства есть цена. Метод разбирает ответ раньше, чем ты его увидишь. Проверка SDK 1.11 на ответах-сбоях, собранных по документации, показала два исхода. Оборванный JSON и отказ с текстом поднимают `pydantic.ValidationError`, и `stop_reason` из исключения не достать. Если текста нет вовсе (отказ до вывода или обрыв ещё на рассуждении), `parsed_output` равен `None`. Когда причины нужно различать, бери `create()` и смотри `stop_reason` до разбора.

Тот же механизм есть у инструментов — функций, которые модель может попросить вызвать. Их аргументы тоже описывает JSON-схема, и поле **`strict: true`** гарантирует, что аргументы вызова ей соответствуют. Подробности будут в уроке про инструменты.

<Callout type="blue" title="Так делали раньше">
Форму добывали двумя приёмами. Первый называется **prefill**. Ответ начинали за модель, например символом `{`, и ей оставалось продолжить JSON. Второй — **форсированный вызов инструмента**. Параметр `tool_choice` с типом `tool` или `any` заставлял модель вызвать инструмент, и аргументы вызова были нужным JSON. На 2026-10 prefill даёт ошибку 400 на моделях Claude 4.6 и новее, а форсированный `tool_choice` — на Opus 5.5, Sonnet 5.5 и Fable 5.1.
</Callout>

<Reveal q="Дашборд показывает: за сутки все запросы со схемой вернули статус 200. Значит ли это, что в каждом ответе лежит JSON по схеме?">
Нет. Отказ и обрыв для API не ошибки. Они приходят со статусом 200 и отличаются только полем `stop_reason`. При `end_turn` модель закончила сама, и ответ можно разбирать. При `refusal` текста может не быть совсем, при `max_tokens` JSON мог оборваться.
</Reveal>

## Как на практике

- **Опиши форму классом.** Для простого случая хватит `parse()`. Чтобы различать сбои, отправляй схему через `create()`, из класса её сделает `transform_schema()`. Повторять формат в промпте незачем, потому что его описание API само добавляет в системный промпт.
- **Делай поля обязательными, а для «нет данных» разреши `null`.** Иначе модель обязана что-то вписать. Лимиты на 2026-10: 24 необязательных поля и 16 полей с несколькими типами на запрос.
- **Закрытый набор значений задавай через `enum`.** В Pydantic это `Literal`.
- **Не заводи в схеме поле для рассуждений.** Поле `reasoning` перед ответом, чтобы модель «подумала», по документации может закончиться отказом. Глубину задаёт effort, а в схеме можно просить короткое объяснение.
- **Проверяй значения своим кодом.** Диапазоны, формат номера, сверку с исходным текстом схема не видит. Дальше называем это **валидацией значений**.
- **Ограничь повторы.** Повтор запроса после сбоя называют **ретраем**. Ретрай с текстом ошибки после провала валидации — инженерная практика, документация её не описывает. Отказ тем же запросом не повторяй. После двух-трёх попыток запись идёт человеку.

## Три разбора

**Разбор 1. Вступление сломало парсер.**
Сервис просит «верни JSON» и вызывает `json.loads`. В проде на части запросов перед объектом появляется «Вот извлечённые данные:», и разбор падает на первом символе. Разработчик дописывает в промпт «БЕЗ ПОЯСНЕНИЙ», но сбои остаются. Ход: описать форму классом и перейти на `parse()`. Вывод: лишний текст вокруг JSON убирает схема в запросе, а формулировка в лучшем случае делает его реже.

**Разбор 2. Схема есть, а JSON не разбирается.**
Сервис вытаскивает из счетов список позиций через `parse()`, `max_tokens` равен 1024. На коротких счетах всё работает, на длинных вызов падает с `ValidationError`.

<Reveal q="Схема передана, грамматика работала. Как думаешь, почему JSON всё равно не разобрался?">
Он не дописан. Грамматика следит за каждым токеном, но закрыть объект не может, если генерацию остановил лимит. В `max_tokens` входят и рассуждение, и сам JSON, поэтому длинный счёт в 1024 токена не поместился. Убедиться в этом можно тем же запросом через `create()`: в `stop_reason` будет стоять `max_tokens`.
</Reveal>

Ход: поднять лимит с запасом на рассуждение, а оборванный ответ считать неудачным и повторять. Вывод: гарантия формы действует для ответа, который модель закончила сама.

**Разбор 3. Где схема лишняя.**
Сервис пишет черновики писем клиентам, текст читает и правит менеджер. Разработчик «для порядка» заворачивает ответ в JSON с одним полем `text`. Форма здесь никому не нужна, а платить за неё приходится. По документации описание формата добавляет входных токенов, а первый запрос с новой схемой ждёт компиляции грамматики. Ход: убрать схему и отдавать обычный текст. Вывод: схема нужна там, где ответ разбирает программа.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| Считать, что схема проверила данные | Гарантирована форма; значение может быть выдуманным | Валидация значений в коде |
| Считать статус 200 успехом | Отказ и обрыв тоже приходят со статусом 200 | Смотреть `stop_reason`; в `parse()` ловить `ValidationError` и `None` |

## Практикум

<Practice title="Спроектируй вывод, который не сломает парсер" checklist={["Форма задана классом или схемой и уходит в запросе", "Для даты, которой может не быть, разрешён null", "Валюта ограничена закрытым списком", "Перечислено, что код проверяет сам, потому что схема этого не гарантирует", "Три сбоя обрабатываются по-разному: отказ, обрыв по max_tokens, провал валидации значений", "Число попыток ограничено, после них запись идёт человеку"]}>
Из писем клиентов нужно извлекать заказ: номер, сумму, валюту и желаемую дату доставки. Номера заказов начинаются с `ORD-`, валют три: рубли, доллары и евро. Дата в письме есть не всегда. Объект без участия человека уходит в учётную систему.

1. Опиши форму: какие поля, каких типов, что обязательно, как быть с датой и валютой.
2. Перечисли, что твой код проверит после разбора.
3. Реши, что делает код при отказе, при обрыве по `max_tokens` и при провале проверки значений.

<div slot="solution">
Рабочий вариант (Python, Anthropic SDK 1.11, сверено с документацией 2026-10-02 — проверь у себя):

```python
from typing import Literal, Optional

import anthropic
import pydantic
from anthropic import transform_schema
from pydantic import BaseModel, Field

client = anthropic.Anthropic()


class Order(BaseModel):
    order_id: str
    amount: float = Field(gt=0)
    currency: Literal["RUB", "USD", "EUR"]
    delivery_date: Optional[str]


FORMAT = {
    "type": "json_schema",
    "schema": transform_schema(Order),
}


def check(text):
    try:
        order = Order.model_validate_json(text)
    except pydantic.ValidationError as e:
        return None, str(e)
    if not order.order_id.startswith("ORD-"):
        return None, "order_id начинается не с ORD-"
    return order, None


def extract(letter):
    prompt = "Извлеки заказ из письма:\n" + letter
    limit = 4096
    for _ in range(2):
        resp = client.messages.create(
            model="claude-opus-5-5",
            max_tokens=limit,
            output_config={"format": FORMAT},
            messages=[{"role": "user", "content": prompt}],
        )
        if resp.stop_reason == "max_tokens":
            limit = 16000
            continue
        if resp.stop_reason != "end_turn":
            return None
        text = next(
            b.text for b in resp.content if b.type == "text"
        )
        order, error = check(text)
        if order:
            return order
        prompt += "\nПрошлый ответ отклонён: " + error
    return None


order = extract("Заказ ORD-1042 на 1500 рублей.")
print(order or "на ручной разбор")
```

- **Форма.** Все четыре поля обязательны. Для письма без даты у модели есть ответ `null`, валюта задана закрытым списком через `Literal`.
- **Что проверяет код.** `model_validate_json` сверяет ответ с классом, включая границу `gt=0`. Формат номера ловит строка с `startswith`. В настоящей системе добавится сверка суммы с письмом.
- **Три ветки.** При обрыве вторая попытка идёт с большим `max_tokens`. При отказе повтора нет, функция сразу возвращает `None`. При плохом значении, включая валюту в другом регистре, вторая попытка получает текст ошибки. После двух попыток письмо уходит человеку.
</div>
</Practice>

<Callout type="teal" title="В работу">
Где в твоей работе ответ модели уже разбирает программа или скоро будет? До пятницы выбери одно такое место и запиши: какая там схема, что код проверяет после разбора и что он делает при отказе и обрыве. Через неделю-две посмотри, сколько ответов ушло в ручной разбор и почему.
</Callout>

## Шпаргалка

| Что | Коротко |
| --- | --- |
| Схема в запросе | `output_config={"format": {"type": "json_schema", "schema": …}}` |
| Короткий путь в Python | `client.messages.parse(output_format=Класс)`, объект в `parsed_output` |
| Что гарантировано | Валидный JSON, обязательные поля, типы |
| Что не гарантировано | Смысл значений, регистр в `enum`, ответ при отказе и обрыве |
| Причина остановки в `create()` | `end_turn` — разбирай, `max_tokens` — ретрай с большим лимитом, `refusal` — человеку |
| Сбой в `parse()` | `ValidationError` или `parsed_output`, равный `None` |
| «Нет данных» | `null` в типе поля; в Pydantic `Optional` |
| Чего схема API не принимает | `minimum`, `maximum`, длину строк, рекурсию; `additionalProperties` только `false` |
| Ошибка 400 (2026-10) | Prefill с Claude 4.6; `tool_choice` с типом `any` или `tool` на Opus 5.5, Sonnet 5.5, Fable 5.1 |
