## Зачем это

Демо работает идеально: просишь модель «верни JSON с полями name и email», код парсит — красота. Выкатываешь в прод, и на сотом запросе модель добавляет «Конечно! Вот результат:» перед JSON, парсер падает, а с ним и твой сервис. Не потому что модель сломалась — потому что «верни JSON» никогда и не было гарантией.

Как только вывод LLM читает не человек, а код, наивный подход «попросить текстом и распарсить» превращается в источник редких, злых, плавающих багов. Есть механизмы, которые дают структуру не как просьбу, а как контракт, — и разница между «обычно работает» и «работает всегда» именно в них.

Итог урока — умение получать машиночитаемый вывод надёжно: через схему и tool use, с валидацией и ретраем вместо веры в то, что модель «поймёт про JSON».

## Ядро: структура как контракт, а не просьба

<Callout type="purple" title="Суть">
Если вывод модели парсит код, тебе нужна **гарантия структуры**, а не вежливая просьба. «Верни только JSON» — это просьба, и модель, генерируя правдоподобное продолжение, может добавить вступление, пояснение или сломать кавычки. Надёжность даёт не формулировка, а механизм: **tool use** (модель обязана вернуть аргументы по заданной схеме) или **structured outputs** (формат ответа задаётся схемой на уровне API). Плюс всегда — валидация и ретрай: даже с механизмом продакшн строится на проверке, а не на доверии.
</Callout>

Это прямое следствие всего курса: модель генерирует правдоподобный текст, а не гарантированную структуру. «Обычно возвращает валидный JSON» и означает «иногда не возвращает» — а «иногда» на потоке запросов случается каждый день.

<Reveal q="Инструкция «верни ТОЛЬКО валидный JSON, без пояснений» — достаточно для продакшна?">
Нет. Она повышает шансы, но не даёт гарантии: модель всё ещё может добавить текст, оборвать вывод на лимите токенов, сломать экранирование в строке. Для разовой задачи сойдёт; для кода, который парсит вывод на потоке, нужен механизм со схемой (tool use / structured outputs) плюс валидация и ретрай. Просьба — не контракт.
</Reveal>

## Как устроено: от просьбы к гарантии

### Почему «верни JSON» ломается

- **Лишний текст.** «Вот ваш JSON:», пояснение после — и `json.loads` падает на первом же символе.
- **Невалидный синтаксис.** Незакрытая кавычка, висячая запятая, неэкранированный перевод строки внутри значения.
- **Обрыв на лимите.** Ответ упёрся в `max_tokens` и оборвался на середине объекта.
- **Дрейф формата.** Сегодня поле называется `email`, завтра `e-mail`, потому что «правдоподобно» и так, и так.

### Tool use — схема как обязательство

Механизм tool use (он же function calling) переворачивает задачу: ты описываешь **инструмент** с JSON-схемой входных аргументов, и модель, вместо свободного текста, возвращает вызов этого инструмента с аргументами, которые обязаны соответствовать схеме.

```python
from anthropic import Anthropic

client = Anthropic()

tools = [{
    "name": "save_contact",
    "description": "Сохранить извлечённый из текста контакт",
    "strict": True,  # жёстко: ответ обязан точно соответствовать схеме
    "input_schema": {
        "type": "object",
        "properties": {
            "name": {"type": "string"},
            "email": {"type": "string"},
        },
        "required": ["name", "email"],
        "additionalProperties": False,
    },
}]

resp = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=512,
    tools=tools,
    tool_choice={"type": "tool", "name": "save_contact"},  # заставить вызвать инструмент
    messages=[{"role": "user", "content": "Извлеки контакт: Иван Петров, ivan@example.com"}],
)
# В ответе — блок tool_use с полем input по схеме: {"name": "...", "email": "..."}
```

`tool_choice` со `type: "tool"` заставляет модель вызвать именно этот инструмент — то есть вернуть данные по схеме, а не абзац текста. Флаг `strict` включает жёсткий режим: ответ обязан точно соответствовать схеме (сам механизм инструментов подробно разбираем в уроке «Инструменты»). Многие вендоры дают и отдельный режим **structured outputs**: формат ответа задаётся схемой прямо в запросе (у Anthropic — через `output_config`/парсинг ответа помощником `messages.parse()`; сверься с докой на 2026-07). Оба пути про одно — сделать структуру частью контракта запроса.

### Оговорка: два приёма из прошлого

Раньше для этой задачи советовали ещё два приёма. Знать их стоит, но с важной оговоркой: на новейших моделях Claude (Opus 4.8, Sonnet 5, Fable 5 — те, что в примерах курса) оба **не работают**.

- **Prefill (префилл).** Идея — начать ответ ассистента за него, например символом `{`, чтобы вступление «Конечно, вот…» стало невозможным. Но на новейших Claude префилл последней реплики ассистента **возвращает ошибку 400** — его роль там закрывают structured outputs и tool use со схемой. Приём остаётся рабочим на старых Claude и у ряда других провайдеров.
- **Температура 0.** Низкая температура снижала разброс вывода. Но, во-первых, на тех же новейших моделях параметр `temperature` вообще **убран** (урок про семплинг), а во-вторых — детерминизм *формы* даёт не сэмплинг, а сам механизм со схемой. Форму держит контракт (tool use / structured outputs), а температура тут ни при чём.

## Как на практике: валидация и ретрай — всегда

Даже с механизмом действует правило: **не доверяй, проверяй.**

Схема + tool use резко снижают частоту сбоев; валидация ловит остаток; ретрай гасит редкие промахи. Вместе это превращает «обычно работает» в «работает надёжно».

<Callout type="blue" title="Почему валидация нужна даже с tool use">
Строгий механизм (strict / structured outputs) гарантирует, что модель вернёт данные *в форме* схемы: правильные поля, правильные типы. Но и он не гарантирует, что значения *осмысленны*: в поле `email` может оказаться строка без «собаки», в `date` — несуществующее число, в `amount` — отрицательная сумма там, где так не бывает. Схема проверяет форму, валидация — смысл. Продакшн-система проверяет и то, и другое, потому что модель по-прежнему генерирует правдоподобное, а не гарантированно верное, — только теперь в жёстких рамках формы.
</Callout>

## Три разбора

**Разбор 1. Пояснение сломало парсер.**
Ты просишь «верни JSON», код делает `json.loads(response)`. В демо всё чисто, в проде на части запросов модель добавляет «Вот извлечённые данные:» перед объектом — и парсер падает с ошибкой на первом символе. Причина не в модели, а в подходе: свободный текст никогда не гарантирован. Лечение: tool use со схемой (или structured outputs), а не вера в формулировку.

**Разбор 2. Tool use даёт валидный объект.**
Та же задача через инструмент `extract_data` с JSON-схемой и `tool_choice`. Модель возвращает не текст, а вызов с аргументами по схеме — поля и типы на месте по построению. Код берёт `input` и работает с ним как с обычным объектом. Класс багов «лишний текст сломал парсинг» исчезает как явление.

**Разбор 3. Невалидное значение поймано валидацией.**
Модель вернула структурно корректный объект, но в поле `email` — «нет данных» вместо адреса. Схема пропустила (это строка), а логика — нет. Валидатор ловит: «email не похож на адрес» — и код уходит в ретрай с уточнением или помечает запись на ручную проверку. Без этого шага мусорное значение утекло бы дальше по системе незаметно.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| Парсить свободный текст модели | Лишний текст и синтаксис ломают парсер | tool use / structured outputs со схемой |
| Верить «верни только JSON» | Просьба — не гарантия структуры | Механизм со схемой (tool use / structured outputs) |
| Не форсировать вызов инструмента | Модель может ответить текстом вместо схемы | `tool_choice` type:"tool" — заставить вернуть данные по схеме |
| Пропустить валидацию | Форма верна, а значение мусорное | Проверять смысл значений, не только форму |
| Нет ретрая на сбой | Редкий промах роняет весь пайплайн | Ограниченный ретрай при провале валидации |
| Полагаться на температуру ради формы | На новых Claude параметр убран, форму держит не сэмплинг | Форму гарантирует механизм со схемой |
| Отдавать сырой ответ дальше | Ошибка утекает в систему незаметно | Дальше идёт только провалидированный объект |

## Практикум

<Practice title="Спроектируй надёжный вывод для парсера" checklist={["Описана JSON-схема нужного результата", "Выбран механизм (tool use / structured outputs), а не «верни JSON»", "Вызов инструмента форсирован (tool_choice), а не оставлен на усмотрение модели", "Есть шаги валидации значений и ретрая при сбое"]}>
Тебе нужно из письма извлекать заказ в объект `{ order_id: string, amount: number, currency: string }`, и этот объект идёт дальше в код автоматически. Спроектируй надёжный вывод:

1. Как задать структуру, чтобы она была контрактом, а не просьбой?
2. Что именно делает форму гарантированной, а не «как получится»?
3. Что проверить в полученном объекте помимо того, что это валидный JSON?
4. Что делать, если проверка не прошла?

<div slot="solution">
- **1.** Описать инструмент (tool use) с `input_schema`: `order_id` (string), `amount` (number), `currency` (string), все `required`, плюс `strict` для жёсткого соответствия; вызвать с `tool_choice` на этот инструмент. Или structured outputs со схемой — если вендор/модель поддерживают. «Верни JSON» текстом не использовать.
- **2.** Сам механизм: `tool_choice` заставляет модель вернуть аргументы по схеме, а `strict`/structured outputs гарантируют форму. Детерминизм структуры даёт контракт, а не параметр семплинга — на новейших Claude `temperature` вообще убран, и полагаться на него ради формы не нужно и нельзя.
- **3.** Смысл значений, не только форму: `order_id` соответствует твоему формату; `amount` положителен и разумен; `currency` — из допустимого списка (RUB/USD/…), а не выдуманный код. Схема проверит типы, валидатор — осмысленность.
- **4.** Ограниченный ретрай: повторить запрос (можно приложив сообщение об ошибке валидации), максимум N попыток; если и после — пометить письмо на ручную обработку, а не пускать мусор дальше.

Смысл: структура — контракт (механизм + схема), а не пожелание; надёжность — валидацией и ретраем. Модель всё ещё генерирует правдоподобное, но теперь в жёстких рамках и под проверкой.
</div>
</Practice>

## Шпаргалка

| Что | Коротко |
| --- | --- |
| «Верни JSON» | Просьба, не гарантия — ломается на потоке |
| tool use | Модель возвращает аргументы по JSON-схеме |
| Structured outputs | Формат ответа задан схемой на уровне API |
| Prefill | Начать ответ за модель (`{`) — но на новых Claude недоступен (400) |
| Детерминизм формы | Даёт механизм со схемой, не температура (на новых Claude она убрана) |
| Схема vs валидация | Схема проверяет форму, валидация — смысл значений |
| Ретрай | Ограниченный повтор при провале валидации |
| Правило | Дальше по системе — только провалидированный объект |
