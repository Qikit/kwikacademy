## Зачем это

В прошлом уроке ты покрыл маршруты и сервис тестами: приложение запускает `testApplication`, базу заменяет репозиторий в памяти. Осталась последняя задача курса. Продакт хочет видеть, сколько раз переходили по каждой короткой ссылке. Проще всего прибавлять клик в базе прямо в обработчике редиректа и только потом отвечать 302.

Работать это будет, но переход начнёт зависеть от базы. Поэтому клики пишут в фоне. Что тогда станет с незаписанными кликами, когда сервер останавливают ради обновления? Кажется, достаточно перестать принимать новые клики, а очередь как-нибудь допишется.

После урока ты сможешь собрать сервис коротких ссылок целиком, с маршрутами, базой, ошибками, DI и тестами, и добавить к нему статистику переходов на корутинах, которая при штатной остановке сервера сохраняет все клики.

## Ядро: сначала дочитать очередь, потом отменять

<Callout type="purple" title="Суть">
Редирект кладёт код ссылки в **канал** (channel) и сразу отвечает, а фоновая корутина-**воркер** (worker) достаёт коды по одному и пишет клики в базу. Воркер живёт в области видимости приложения, и при остановке Ktor её отменяет. Чтобы клики не пропали, до отмены канал закрывают и **дожидаются воркера**: сначала `close()`, потом `join()`.
</Callout>

Счётчик — один класс `ClickCounter` и две строки в DI.

Прежде чем раскрыть ответ, ответь сам, хотя бы про себя.

## Как устроено: канал и воркер

**Канал** из kotlinx.coroutines — очередь между корутинами. Документация сравнивает его с `BlockingQueue`: вместо блокирующих `put` и `take` у него приостанавливающие `send` и `receive`, и его можно закрыть. В сокращателе канал стоит между редиректом и базой, а в сервисе рассылки встал бы между разбором загруженного файла и отправкой писем. Контрпример — холодный `Flow` из урока про Flow: он ничего не хранит и на каждый `collect` выполняет код внутри `flow { }` заново. Канал хранит отправленное, пока его не заберут.

По умолчанию буфера у канала нет. Такой канал называют **rendezvous** (встреча), и `send` в нём ждёт, пока кто-то вызовет `receive`. **`Channel.UNLIMITED`** даёт буфер без ограничения, поэтому отправитель не ждёт никогда, а число элементов ограничено только памятью. Клик кладут через **`trySend`**: функция не приостанавливается, не бросает исключений и возвращает результат. Неудача бывает, когда буфер полон или канал закрыт, у неограниченного буфера — только второе.

**Воркер** — фоновая корутина, которая читает канал циклом `for (code in clicks)`. Пока канал открыт, цикл ждёт новых кодов. После `close()` он получает всё, что отправили до закрытия, и заканчивается.

В примере ниже `isSuccess` говорит, удалась ли отправка, а `merge` прибавляет единицу к счётчику кода или кладёт 1 для нового. Playground работает на Kotlin 2.4.20 с kotlinx.coroutines 1.7.3. С 1.11.0, на которой собран проект, вывод тот же. Предскажи, в каком порядке появятся строки:

<KotlinPlayground>

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.channels.Channel

fun main() = runBlocking {
    val clicks = Channel<String>(Channel.UNLIMITED)
    val counts = mutableMapOf<String, Int>()
    val worker = launch {
        for (code in clicks) {
            counts.merge(code, 1, Int::plus)
            println("записан клик $code")
        }
        println("воркер закончил")
    }
    for (code in listOf("ktor", "kotlin", "ktor")) {
        val sent = clicks.trySend(code).isSuccess
        println("редирект $code, в очереди: $sent")
    }
    clicks.close()
    worker.join()
    println(counts)
}
```

</KotlinPlayground>

<Reveal q="В каком порядке программа напечатает строки про редиректы и клики?">
Сначала три строки «редирект …, в очереди: true», потом три «записан клик …», «воркер закончил» и `{ktor=2, kotlin=1}`. `launch` только планирует запуск воркера, а `trySend` не приостанавливается, поэтому `main` отправляет все коды, не уступая поток выполнения (thread). Воркер стартует на `join()` и забирает накопленное. Так и редирект в сервисе отвечает, не дожидаясь записи.
</Reveal>

Запусти, потом замени `Channel<String>(Channel.UNLIMITED)` на `Channel<String>()` и предскажи вывод.

## Как устроено: остановка без потерь

Воркеру нужна область видимости, и Ktor даёт её сам: класс `Application` реализует `CoroutineScope`. По справочнику Ktor её отменяют при остановке приложения, и в ней удобно запускать фоновые корутины. Программа ниже моделирует остановку: `appJob` играет роль `Job` приложения, а запись клика изображает `delay(100)`. `coroutineContext` — контекст корутины `runBlocking`, а `+ appJob` подменяет в нём `Job`: воркер работает в том же потоке выполнения, но отменяется через `appJob`.

<KotlinPlayground>

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.channels.Channel

class ClickCounter(scope: CoroutineScope) {
    private val clicks = Channel<String>(Channel.UNLIMITED)
    var saved = 0
        private set
    private val worker = scope.launch {
        for (code in clicks) {
            delay(100) // запись в базу
            saved++
        }
    }

    fun record(code: String) {
        clicks.trySend(code)
    }

    suspend fun close() {
        clicks.close()
    }
}

fun main() = runBlocking {
    val appJob = Job()
    val app = CoroutineScope(coroutineContext + appJob)
    val counter = ClickCounter(app)
    repeat(5) { counter.record("ktor") }
    delay(250) // сервер работает

    counter.close() // ApplicationStopping
    appJob.cancelAndJoin() // Ktor отменяет корутины
    println("Сохранено ${counter.saved} из 5")
}
```

</KotlinPlayground>

<Reveal q="Сначала предскажи: сколько кликов из пяти сохранит программа?">
Два: «Сохранено 2 из 5». За 250 мс воркер записал два клика и стоял в `delay` над третьим. `close()` только закрыл канал: три кода ещё лежали в очереди, когда `cancelAndJoin()` отменил воркер в точке приостановки. Закрытие запрещает новые элементы, но не ждёт, пока старые разберут.
</Reveal>

Допиши в `close()` вторую строку, `worker.join()`, и запусти снова: выйдет «Сохранено 5 из 5». В проекте класс устроен так же, только пишет в базу:

```kotlin
class ClickCounter(
    private val repository: LinkRepository,
    scope: CoroutineScope,
) : AutoCloseable {
    private val clicks = Channel<String>(Channel.UNLIMITED)
    private val worker = scope.launch { saveClicks() }

    fun record(code: String) {
        clicks.trySend(code)
    }

    override fun close() {
        clicks.close()
        runBlocking { worker.join() }
    }

    private suspend fun saveClicks() {
        for (code in clicks) {
            try {
                repository.addClick(code)
            } catch (e: SQLException) {
                log.warn("Click for '$code' was not saved", e)
            }
        }
    }

    private companion object {
        val log = LoggerFactory.getLogger(ClickCounter::class.java)
    }
}
```

`close()` из `AutoCloseable` не suspend-функция, поэтому воркер ждут через `runBlocking`. `try` ловит ошибку записи одного клика: без него первая же `SQLException` завершит воркер, а `trySend` продолжит складывать клики в канал, который никто не читает. Широкий `catch (e: Exception)` проглотил бы и `CancellationException`, как в уроке про корутины под контролем: при отмене воркер записал бы остаток очереди в лог как ошибки базы. `log` — логгер SLF4J, новая зависимость ему не нужна: библиотека приходит с Ktor.

Область видимости счётчик получает в DI, а редирект вызывает `record` перед ответом:

```kotlin
fun Application.configureDependencies() {
    val appScope: CoroutineScope = this
    dependencies {
        provide(::connectDatabase)
        provide<LinkRepository>(::ExposedLinkRepository)
        provide<CodeGenerator> { RandomCodeGenerator() }
        provide(::LinkService)
        provide { ClickCounter(resolve(), appScope) }
    }
}

// Routing.kt
val clickCounter: ClickCounter = dependencies.resolve()
// …
get("/{code}") {
    val link = service.resolve(call.requirePathParameter("code"))
    clickCounter.record(link.code)
    call.respondRedirect(link.url)
}
```

`this` сохраняют в `appScope` до блока: внутри `dependencies { }` неявный получатель `Application` закрыт маркером DSL. При остановке DI сам закрывает зависимости с `AutoCloseable`, в порядке, обратном объявлению. Счётчик объявлен последним и закрывается первым, пока репозиторий и база ещё работают.

<Reveal q="В документации Ktor пример освобождения ресурсов подписан на событие ApplicationStopped. Почему бы не закрыть счётчик там?">
К `ApplicationStopped` воркера уже нет. Между `ApplicationStopping` и `ApplicationStopped` Ktor отменяет область видимости приложения, воркер получает отмену в ближайшей точке приостановки, и очередь читать некому. `ApplicationStopped` годится для закрытия соединений, а работу, которой нужны корутины приложения, заканчивают в `ApplicationStopping`.
</Reveal>

Порядок остановки в Ktor 3.6.0, по исходному коду сервера:

1. Движок останавливается и даёт текущим запросам время доработать.
2. `ApplicationStopping`: DI закрывает зависимости, `close()` счётчика ждёт воркер.
3. Ktor отменяет область видимости приложения и ждёт её корутины.
4. `ApplicationStopped`.

Запускает остановку **обработчик завершения** JVM (shutdown hook), который Ktor регистрирует при старте сервера. Ctrl+C его запускает, а при `kill -9` или `taskkill /F` процесс убивает ОС: обработчик не запускается, и очередь пропадает.

<Callout type="blue" title="Если знаешь Java — здесь иначе">
В Java такую схему собирают из `BlockingQueue` и потока выполнения. Закрытия у `BlockingQueue` нет, и Javadoc называет обычным приёмом объект-маркер конца (poison object). Пул потоков выполнения останавливают в два шага: `shutdown()` не принимает новых задач, но старых не ждёт, дождаться их помогает `awaitTermination()`. С Java 19 оба шага делает `close()`. В Kotlin шаги те же, `close()` и `join()`, только закрытие встроено в канал.
</Callout>

## Как на практике

- **Запускай воркер в области видимости приложения.** Передавай её параметром, как в `ClickCounter(repository, scope)`: корутину остановит владелец области.
- **Закрывай в `ApplicationStopping`.** Проще всего через `AutoCloseable` и DI, объявив счётчик после того, что он использует.
- **Сначала `close()`, потом `join()`.** В обратном порядке остановка зависнет: цикл по открытому каналу ждёт вечно.
- **Считай атомарно, даже если пишет один воркер.** В памяти — `merge` у `ConcurrentHashMap`, в базе — `clicks + 1`, которое база вычисляет сама в одном `UPDATE`. Появится второй писатель, и клики не потеряются.

<Callout type="teal" title="Как принято">
Фоновые корутины не запускают в `GlobalScope`. Руководство Android по корутинам объясняет почему: такой код выполняется в неуправляемой области видимости, и тестировать его очень трудно. Внешнюю область видимости передают параметром, а создаёт её и управляет ею объект, который живёт дольше вызывающего кода. В Ktor это само `Application`, в тесте — приложение из `testApplication`.
</Callout>

## Три разбора

**Разбор 1. Тест, который ловит потерю.**
Тест `saves every click before the application stops` делает 50 переходов, а репозиторий-обёртка `SlowClicksRepository` добавляет `delay(10)` к каждой записи, так что к остановке в канале стоит очередь. `testApplication` в конце сам останавливает приложение, и тест проверяет, что сохранены все 50. Без `join()` в `close()` тест падает с `expected: <50> but was: <5>`: 45 кликов пропали. Вывод: тест на остановку должен создавать очередь, иначе он проверяет пустой канал.

**Разбор 2. 500 переходов и Ctrl+C.**
Мы проверили остановку на проекте с файловой базой H2. По ссылке сделали 500 переходов, по 25 одновременно, и сразу запросили `/stats`. В нашем прогоне ответ был 398: статистика отстаёт от переходов на длину очереди. Тут же нажали Ctrl+C, и процесс завершился секунд через пять: воркер дописывал очередь. После перезапуска на той же базе `/stats` показал 500. Вывод: редирект отвечает сразу, а воркер дописывает очередь позже, даже во время остановки.

**Разбор 3. Где очередь в памяти не спасает.**
Канал живёт в памяти процесса. Если процесс убьёт ОС, обработчик завершения не запустится, и очередь пропадёт. Для статистики переходов это терпимо, а клик, за который платит рекламодатель, пишут в базу до ответа, как предлагал коллега. Вывод: канал с воркером подходит там, где потерю при аварии можно пережить.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| `close()` без `join()` | Воркер отменят с неразобранной очередью: в тесте уцелело 5 кликов из 50 | После `close()` дождаться `worker.join()` |
| `trySend` в канал без буфера | Клик проходит, только если воркер уже ждёт в `receive`: с `Channel<String>()` первый пример печатает три `false` и `{}` | `Channel.UNLIMITED` или ограниченный буфер |
| Закрывать счётчик в `ApplicationStopped` | Воркер к этому моменту отменён | `ApplicationStopping` через `AutoCloseable` и DI |
| Цикл воркера без `try` или с `catch (e: Exception)` | Ошибка базы убивает воркер, широкий `catch` глотает отмену | `catch (e: SQLException)` вокруг записи клика |
| Счётчик через «прочитал, прибавил, записал» | Два писателя прочитают одно значение, и клик пропадёт | `merge(code, 1, Long::plus)` или `clicks + 1` в SQL |

```kotlin
// LinkRepository.kt
suspend fun addClick(code: String)

suspend fun findClicks(code: String): Long?

// ExposedLinkRepository.kt
override suspend fun addClick(code: String) {
    dbQuery {
        LinksTable.update({ LinksTable.code eq code }) {
            it[clicks] = clicks + 1
        }
    }
}

override suspend fun findClicks(code: String): Long? =
    dbQuery {
        selectByCode(code).singleOrNull()?.get(LinksTable.clicks)
    }

// InMemoryLinkRepository.kt
private val clicks = ConcurrentHashMap<String, Long>()

override suspend fun addClick(code: String) {
    clicks.merge(code, 1, Long::plus)
}

override suspend fun findClicks(code: String): Long? =
    links[code]?.let { clicks[code] ?: 0 }

// LinkService.kt
suspend fun countClicks(code: String): Long =
    repository.findClicks(code) ?: throw LinkNotFoundException(code)

// Dto.kt
@Serializable
data class LinkStatsResponse(
    val code: String,
    val clicks: Long,
)

// Routing.kt, внутри route("/api/links")
get("/{code}/stats") {
    val code = call.requirePathParameter("code")
    val clicks = service.countClicks(code)
    call.respond(LinkStatsResponse(code, clicks))
}
```

```kotlin
import io.ktor.client.call.body
import io.ktor.client.request.get
import io.ktor.http.HttpStatusCode
import io.ktor.server.testing.testApplication
import kotlinx.coroutines.delay
import kotlinx.coroutines.test.runTest
import kotlin.test.Test
import kotlin.test.assertEquals

class StatsApiTest {
    @Test
    fun `returns click statistics`() =
        testApplication {
            val repository = InMemoryLinkRepository()
            setUpShortener(repository)
            val client = jsonClient()
            client.createLink("https://ktor.io", alias = "ktor")
            repeat(3) { repository.addClick("ktor") }

            val response = client.get("/api/links/ktor/stats")

            assertEquals(HttpStatusCode.OK, response.status)
            assertEquals(LinkStatsResponse("ktor", 3), response.body())
        }

    @Test
    fun `returns 404 for statistics of an unknown code`() =
        testApplication {
            setUpShortener()

            val response = jsonClient().get("/api/links/nope42/stats")

            assertEquals(HttpStatusCode.NotFound, response.status)
        }

    @Test
    fun `saves every click before the application stops`() {
        val repository = SlowClicksRepository(InMemoryLinkRepository())

        testApplication {
            setUpShortener(repository)
            val client = jsonClient()
            client.createLink("https://ktor.io", alias = "ktor")
            repeat(CLICKS) { client.get("/ktor") }
        }

        runTest {
            assertEquals(CLICKS.toLong(), repository.findClicks("ktor"))
        }
    }

    private class SlowClicksRepository(
        private val delegate: LinkRepository,
    ) : LinkRepository by delegate {
        override suspend fun addClick(code: String) {
            delay(10)
            delegate.addClick(code)
        }
    }

    private companion object {
        const val CLICKS = 50
    }
}
```

`LinkRepository by delegate` — делегирование: функции интерфейса компилятор создаёт сам и передаёт вызовы в `delegate`, а `addClick` переопределена. `testApplication` идёт в реальном времени, поэтому `delay(10)` не пропускается. Первый тест кладёт клики прямо в репозиторий, чтобы не зависеть от очереди.

## Что дальше

Развивать сервис можно по документации Ktor: её учебник по Exposed заканчивается переходом на PostgreSQL, плагин Authentication закроет создание ссылок от чужих, а RateLimit ограничит число запросов клиента и на лишние ответит 429.

На этом курс закончен: от первой программы ты дошёл до сервиса с базой, тестами и корутинами. За языком возвращайся в документацию на kotlinlang.org.

## Шпаргалка

| Что | Коротко |
| --- | --- |
| Очередь событий | `Channel<String>(Channel.UNLIMITED)` |
| Отправить, не ожидая | `trySend(x)`: не приостанавливается, не бросает |
| Воркер | `scope.launch { for (x in channel) … }` |
| Остановка без потерь | `channel.close()`, затем `worker.join()` |
| Где закрывать | `ApplicationStopping`: DI закрывает `AutoCloseable` в обратном порядке |
| Фон в Ktor | область `Application`; `this` сохранить до `dependencies { }` |
| Атомарный счётчик | `merge(code, 1, Long::plus)`; в Exposed `clicks + 1` |
| Остановка сервера | Ctrl+C; при `kill -9` очередь пропадает |
