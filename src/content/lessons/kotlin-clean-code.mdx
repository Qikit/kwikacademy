## Зачем это

В прошлом уроке ты выбирал, как функция сообщает о неудаче: исключение, `null`, sealed-тип или `Result`. Теперь о коде, который работает без ошибок, но который страшно трогать. Нужно добавить доставку в постамат, а в сервисе функция `calc(w, z, t, fl, vip)`: пять параметров, комментарии вместо имён и проверки `t == "courier"` в двух функциях. Одну ты поправишь, вторую не заметишь, и срок доставки в постамат молча посчитается как для почты.

Первое желание — переписать всё с нуля или отложить до «спринта на техдолг». Есть третий путь, и Мартин Фаулер посвятил ему книгу: рефакторинг маленькими шагами. Когда за него браться, Фаулер и Кент Бек предложили решать не по вкусу, а по **запахам кода**, признакам, которые видно с первого взгляда.

После урока ты сможешь найти в коде запахи из «Рефакторинга», назвать рефакторинг, который их убирает, и провести его маленькими шагами, сверяя вывод программы после каждого.

## Ядро: структура меняется, поведение остаётся

<Callout type="purple" title="Суть">
**Рефакторинг** (refactoring) — изменение внутренней структуры программы, после которого её легче понять и дешевле менять, а **наблюдаемое поведение** (observable behavior) остаётся прежним. Его делают цепочкой маленьких шагов, и после каждого программа работает. Что улучшать, подсказывают **запахи кода** (code smells), к чему стремиться — четыре правила простого дизайна Кента Бека.
</Callout>

Отсюда рабочий ритм: маленький шаг, запуск, сравнение с прошлым выводом. Разошлось — виноват последний шаг, и искать недолго.

Прежде чем раскрыть ответ, ответь сам, хотя бы про себя.

<Reveal q="Коллега переименовал calc в deliveryCost и заодно поправил ошибку в скидке. Вывод изменился в двух строках из пяти. Как проверить, что переименование ничего не сломало?">
По выводу — никак, пока правки смешаны. Переименование — рефакторинг и вывод менять не должно, а исправление скидки меняет его нарочно. Какая строка поменялась из-за исправления, а какая из-за ошибки при переименовании, не различить. Откати исправление, сверь вывод с прежним и только потом верни его отдельным шагом.
</Reveal>

## Как устроено: четыре правила простого дизайна

Кент Бек сформулировал правила в конце 1990-х, когда создавал экстремальное программирование (XP). В пересказе Фаулера код с **простым дизайном** (simple design):

1. проходит тесты (passes the tests);
2. выражает намерение (reveals intention);
3. не содержит дублирования (no duplication);
4. состоит из минимума элементов (fewest elements).

Правила идут по приоритету: работающий код важнее выразительного. «Выражает намерение» значит, что по коду понятно, чего хотел автор: `deliveryCost(shipment, delivery)` говорит больше, чем `calc(w, z, t)`. Порядок второго и третьего правил Фаулер считает неважным: они подпитывают друг друга. Четвёртое велит убрать всё, что не служит первым трём.

Тестов у нас пока нет, поэтому первое правило проверяем выводом: он должен совпасть с прежним. В проекте это делают автотесты, и рефакторят только при зелёных тестах. Писать их будем в уроке про тестирование сервиса.

**YAGNI** (You Aren't Gonna Need It, «тебе это не понадобится») — принцип из того же XP: функциональность, которая понадобится когда-нибудь потом, сейчас не пишут. Такая «гибкость на вырост» отнимает время, а пока ею никто не пользуется, мешает менять код рядом. На рефакторинг YAGNI не распространяется: откладывать функциональность можно, только если код легко менять, а таким его держит рефакторинг.

С третьим правилом связан принцип **DRY** (Don't Repeat Yourself, «не повторяйся»). Дэйв Томас и Энди Хант в The Pragmatic Programmer формулируют его так: у каждого знания в системе должно быть единственное, однозначное и авторитетное представление. Их проверка: если одна деталь меняется и править её приходится в нескольких местах, код нарушает DRY. Наценка 50 рублей за этаж в расчёте цены и в тексте чека — как раз такой случай: тариф поменяют, одно место забудут.

Проверь, как ты понял DRY:

<Reveal q="В винном интернет-магазине две проверки: isValidAge проверяет, что возраст больше нуля, а isValidQuantity — что больше нуля число бутылок. Тела у функций одинаковые. Ревьюер требует слить их в одну isPositive, ссылаясь на DRY. Прав ли он?">
Нет. Код совпадает, а знания разные: правило про возраст покупателя и правило про число бутылок. Когда магазин поднимет минимальный возраст до 18, общая функция запретит заказ пяти бутылок. Этот пример разбирают сами Томас и Хант и называют такое совпадением, а не дублированием. Сливают код, который выражает одно знание.
</Reveal>

## Как устроено: запахи и рефакторинги

**Запах кода** — поверхностный признак, который обычно указывает на более глубокую проблему. Запах заметен сразу, но это лишь повод присмотреться: бывают и хорошие длинные функции.

Вот семь запахов из второго издания «Рефакторинга» и рефакторинги против них. Русские названия запахов — как в переводе книги.

| Запах | Как выглядит в Kotlin | Рефакторинг |
| --- | --- | --- |
| Таинственное имя (Mysterious Name) | `calc`, `t`, `p`: не понять без чтения тела | Change Function Declaration, Rename Variable |
| Дублируемый код (Duplicated Code) | Одна формула в двух функциях | Extract Function |
| Длинная функция (Long Function) | Блоки, подписанные комментариями | Extract Function с именем из комментария |
| Длинный список параметров (Long Parameter List) | `calc(2, 3, "courier", 4, false)` | Introduce Parameter Object, Remove Flag Argument |
| Одержимость примитивами (Primitive Obsession) | Статус строкой, `userId: Long` рядом с `orderId: Long` | Replace Primitive with Object: enum, `value class`; если по статусу ветвятся — Replace Type Code with Subclasses |
| Повторяющиеся switch (Repeated Switches) | Одинаковая цепочка `if` или `when` по типу в разных функциях | Replace Conditional with Polymorphism: методы в вариантах sealed-типа |
| Теоретическая общность (Speculative Generality) | Параметры и абстракции «на будущее», которыми никто не пользуется | Change Function Declaration для лишних параметров, Collapse Hierarchy и Inline Class |

<Reveal q="Функцию объявили как send(to: String, subject: String, body: String, html: Boolean, urgent: Boolean) и вызывают send(a, b, c, true, false). Какие запахи ты видишь и с чего начнёшь?">
Длинный список параметров: в вызове не понять, где тема, где текст, а два флага читаются как загадка. И одержимость примитивами: три `String` подряд легко перепутать, компилятор промолчит. Дешёвый первый шаг — именованные аргументы: `html = true`. Если адрес, тема и текст ходят вместе, заведи `data class Letter`, а флаг `html` замени двумя функциями.
</Reveal>

## Рефакторинг по шагам

Вот код доставки из начала урока. Запусти его и запиши пять чисел: после каждого шага они не должны меняться.

<KotlinPlayground>

```kotlin
fun calc(
    w: Int, z: Int, t: String, fl: Int, vip: Boolean
): Int {
    // базовая цена: вес и зона
    var p = w * 30 + z * 150
    // доставка
    if (t == "courier") p += fl * 50
    if (t == "pickup") p /= 2
    // скидка постоянным клиентам
    if (vip) p = p * 90 / 100
    return p
}

fun days(t: String, z: Int): Int {
    if (t == "courier") return z + 1
    if (t == "pickup") return z + 3
    return z + 5
}

fun main() {
    println(calc(2, 3, "courier", 4, false))
    println(calc(2, 3, "pickup", 0, true))
    println(calc(5, 1, "post", 0, false))
    println(days("courier", 3))
    println(days("post", 1))
}
```

</KotlinPlayground>

Делай шаги в редакторе урока и запускай после каждого. Автоматических рефакторингов в нём нет, поэтому имена меняй руками. Сочетания IntelliJ IDEA из шагов и меню рефакторингов Ctrl+Alt+Shift+T (раскладка Windows и Linux) попробуй, скопировав код в проект.

1. **Переименуй** (Rename Variable, Change Function Declaration): `calc` в `deliveryCost`, `days` в `deliveryDays`, короткие имена — в `weightKg`, `zone`, `type`, `floor` и `price`. В IntelliJ IDEA это Shift+F6: имя меняется вместе со всеми ссылками.
2. **Выдели функции** (Extract Function) из блоков под комментариями. Имя берётся из комментария, и сам он становится не нужен. В IDE — Ctrl+Alt+M. Одинаковые вызовы при этом не склеивай: если вызов меняет что-то снаружи, например списывает товар со склада, это **побочный эффект** (side effect), и один вызов вместо двух изменит результат.

```kotlin
fun basePrice(weightKg: Int, zone: Int) =
    weightKg * 30 + zone * 150

fun vipDiscount(price: Int) = price * 90 / 100
```

<Reveal q="Коллега на втором шаге записал скидку короче: price / 100 * 90, «это же то же самое». Сначала предскажи, что теперь напечатает вторая строка программы.">
180 вместо 229. У VIP-самовывоза цена до скидки 255, а `Int` делится нацело: `255 / 100` даёт 2, и `2 * 90` — 180. В исходной формуле умножение идёт первым: 22 950, делённое на 100, даёт 229. Компилятор принимает обе формулы, и подмену ловит только сравнение вывода.
</Reveal>

3. **Замени код типа подклассами** (Replace Type Code with Subclasses). Строка `type` — код типа: по ней выбирают, как считать. Вместе с `floor`, который нужен только курьеру, она превращается в sealed-интерфейс из урока про моделирование с классом на каждый тип доставки, а цепочки `if` — в `when` без `else`:

```kotlin
sealed interface Delivery
data class Courier(val floor: Int) : Delivery
data object Pickup : Delivery
data object Post : Delivery

// внутри deliveryCost
val base = basePrice(weightKg, zone)
val price = when (delivery) {
    is Courier -> base + delivery.floor * 50
    Pickup -> base / 2
    Post -> base
}
```

4. **Перенеси ветки в типы** (Replace Conditional with Polymorphism). Два `when` по `delivery` в разных функциях — это и есть повторяющиеся switch. Каждая ветка становится методом `cost` или `days` своего варианта, и всё про курьера лежит в `Courier`.
5. **Собери параметры в объект** (Introduce Parameter Object): вес и зона ходят вместе и становятся `data class Shipment`. Флаг `vip` остаётся: в сервисе он приходит из профиля покупателя. Двумя функциями заменяют флаг, который стоит в вызове литералом `true` или `false`. Значение из данных передают параметром и называют по имени, как соглашения Kotlin советуют для `Boolean`.

Результат:

<KotlinPlayground>

```kotlin
data class Shipment(val weightKg: Int, val zone: Int)

sealed interface Delivery {
    fun cost(base: Int): Int
    fun days(zone: Int): Int
}

data class Courier(val floor: Int) : Delivery {
    override fun cost(base: Int) = base + floor * 50
    override fun days(zone: Int) = zone + 1
}

data object Pickup : Delivery {
    override fun cost(base: Int) = base / 2
    override fun days(zone: Int) = zone + 3
}

data object Post : Delivery {
    override fun cost(base: Int) = base
    override fun days(zone: Int) = zone + 5
}

fun basePrice(shipment: Shipment) =
    shipment.weightKg * 30 + shipment.zone * 150

fun vipDiscount(price: Int) = price * 90 / 100

fun deliveryCost(
    shipment: Shipment,
    delivery: Delivery,
    vip: Boolean,
): Int {
    val price = delivery.cost(basePrice(shipment))
    return if (vip) vipDiscount(price) else price
}

fun main() {
    val box = Shipment(weightKg = 2, zone = 3)
    val courier = Courier(floor = 4)
    println(deliveryCost(box, courier, vip = false))
    println(deliveryCost(box, Pickup, vip = true))
    println(deliveryCost(Shipment(5, 1), Post, vip = false))
    println(courier.days(zone = 3))
    println(Post.days(zone = 1))
}
```

</KotlinPlayground>

Запусти: те же пять чисел. Потом замени числа 30, 150 и 50 константами с именами и снова сверь вывод. В каталоге это Replace Magic Literal, а detekt из урока про стиль называет такие числа магическими (правило MagicNumber).

<Callout type="blue" title="Если знаешь Java — забытый switch здесь не промолчит">
Повторяющиеся switch вредны тем, что при новом случае их все нужно найти и обновить. Инструкцию `switch` по sealed-интерфейсу javac с Java 21 проверяет на полноту, а по enum и `String` ради совместимости — нет (JEP 441): javac 24 и 26 молчат о забытой константе даже с `-Xlint:all`. В Kotlin `when` без `else` проверяется и по enum, и по sealed-типу, даже когда это инструкция. Добавь `data object Locker : Delivery` в код третьего шага, и компилятор укажет на оба `when`. Обновлять их всё равно придётся по одному, поэтому ветки переносят в типы уже тогда, когда одинаковых `when` два.
</Callout>

## Как на практике

- **Сначала сделай изменение простым.** «Make the change easy, then make the easy change», — так Бек сформулировал **подготовительный рефакторинг** (preparatory refactoring): перед новой фичей приведи код в форму, в которую она ляжет сама.
- **Прибирай по пути.** Правило походной стоянки: оставь код лучше, чем нашёл. Понял, что делает блок, — вырази это в имени.
- **Комментарий «что» превращай в функцию.** Комментарий оставь для «почему»: он объясняет, зачем сделано так и в чём автор не уверен.
- **Держи функции короткими.** Роберт Мартин во втором издании Clean Code советует делать большинство функций в несколько строк: тогда у каждой хорошее имя и одно дело.
- **Разделяй ответственности.** Мартин объясняет принцип единственной ответственности (Single Responsibility Principle) через тех, кто просит изменений: налоги меняют одни люди, скидки другие. Разнеси их расчёты по функциям, и правка налога вряд ли заденет скидку.

<Callout type="teal" title="Как принято">
У Кента Бека есть метафора двух шляп. В шляпе рефакторинга каждая правка сохраняет наблюдаемое поведение и тесты остаются зелёными. В шляпе добавления функциональности ты меняешь поведение: пишешь новые тесты, а старые могут сломаться. Менять шляпы можно хоть каждые пару минут, но носить обе сразу нельзя. Как разнести такие правки по коммитам, разберём в уроке про командную работу.
</Callout>

## Три разбора

**Разбор 1. Постамат.**
Нужен постамат, а тип доставки — строка с проверками в двух функциях. Ход — подготовительный рефакторинг: шаги 1–4 в шляпе рефакторинга, запуск, и только потом `data object Locker : Delivery`. Компилятор ответит «Object 'Locker' is not abstract and does not implement abstract members» (Kotlin 2.4.20) и перечислит `cost` и `days`. Вывод: подготовка превращает поиск по проекту в список ошибок компиляции.

**Разбор 2. Переписать за неделю.**
Коллега неделю переписывал модуль заказов в своей ветке и вернулся с тысячей изменённых строк, конфликтами и двумя багами неизвестного происхождения. Ход: команда договаривается о целевой структуре, а дальше в обычной работе шаг за шагом приближает к ней код, и он всё время остаётся рабочим. Вывод: большую перестройку тоже собирают из маленьких шагов.

**Разбор 3. Скрипт на один запуск.**
Скрипт переносит данные из старой базы, его запустят один раз и удалят. В нём длинная функция и таинственные имена. Рефакторинг окупается более быстрой работой потом, а здесь никакого «потом» нет. Вывод: запах — повод подумать, а чинить стоит код, который будут читать и менять.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| Рефакторинг и новое поведение в одной правке | Разошёлся вывод, и непонятно, где ошибка | Одна шляпа за раз |
| Слить похожий код с разным смыслом | Правка одного правила ломает другое | Сливать только одно знание |
| Вынести в переменную одинаковые вызовы, которые что-то меняют | Вызовов становится меньше, и вывод меняется | Сначала проверить, есть ли у вызова побочный эффект |
| Абстракции и параметры «на будущее» | Их надо поддерживать, а пользы нет | Добавить, когда понадобятся |
| Переименовывать поиском и заменой текста | Заденет чужие одноимённые символы | Rename в IDE: Shift+F6 |

<Practice title="Отрефактори расчёт билетов в кино" checklist={["Вывод совпадает с исходным построчно, все четыре строки", "Ни одного однобуквенного имени у функций, параметров и переменных", "Тип места — enum или sealed-тип, строки «vip» и «sofa» в логике не сравниваются", "Цена и подпись места лежат рядом, в самом типе", "Блоки под комментариями стали функциями или данными типа, комментарии «что» удалены", "Boolean при вызове передаётся по имени"]}>
Функция ниже считает цену билета, а соседняя подписывает место. Отрефактори их маленькими шагами, после каждого сверяя четыре строки вывода с исходными.

<KotlinPlayground>

```kotlin
fun t(a: Int, s: String, st: Boolean): Int {
    // цена места
    var r = 0
    if (s == "vip") r = 900
    if (s == "sofa") r = 700
    if (s == "std") r = 400
    // детям до 12 — половина, студентам — минус 100
    if (a < 12) r = r / 2
    if (st) r = r - 100
    return r
}

fun n(s: String): String {
    if (s == "vip") return "VIP-кресло"
    if (s == "sofa") return "диван"
    return "обычное место"
}

fun main() {
    println(n("vip") + ": " + t(30, "vip", false))
    println(n("sofa") + ": " + t(10, "sofa", false))
    println(n("std") + ": " + t(20, "std", true))
    println(n("std") + ": " + t(8, "std", true))
}
```

</KotlinPlayground>

<div slot="solution">
Рабочий вариант:

```kotlin
enum class Seat(val title: String, val price: Int) {
    VIP("VIP-кресло", 900),
    SOFA("диван", 700),
    STANDARD("обычное место", 400),
}

fun childPrice(price: Int, age: Int) =
    if (age < 12) price / 2 else price

fun studentPrice(price: Int, student: Boolean) =
    if (student) price - 100 else price

fun ticketPrice(age: Int, seat: Seat, student: Boolean) =
    studentPrice(childPrice(seat.price, age), student)

fun printTicket(age: Int, seat: Seat, student: Boolean) {
    val price = ticketPrice(age, seat, student)
    println("${seat.title}: $price")
}

fun main() {
    printTicket(age = 30, Seat.VIP, student = false)
    printTicket(age = 10, Seat.SOFA, student = false)
    printTicket(age = 20, Seat.STANDARD, student = true)
    printTicket(age = 8, Seat.STANDARD, student = true)
}
```

Программа печатает те же четыре строки. Две цепочки `if` по строке стали свойствами enum. Enum здесь лучше sealed-типа, потому что у всех мест одинаковый набор данных: подпись и цена. Порядок скидок сохранён: поменяешь его, и последняя строка покажет 150 вместо 100.
</div>

## Шпаргалка

| Что | Коротко |
| --- | --- |
| Рефакторинг | Структура меняется, наблюдаемое поведение нет |
| Правила Бека | Тесты, намерение, без дублирования, минимум элементов |
| DRY | Одно место для каждого знания |
| YAGNI | Не писать функциональность, пока она не нужна |
| Две шляпы | Рефакторинг или новое поведение, не вместе |
| IntelliJ IDEA | Ctrl+Alt+Shift+T — меню, Shift+F6 — Rename, Ctrl+Alt+M — Extract |
| Длинный список параметров | Именованные аргументы, `data class`-параметр, без флагов-литералов |
| Одержимость примитивами | `value class`, enum; код типа — sealed-тип |
| Повторяющиеся switch | Методы в вариантах sealed-типа |
