## Зачем это

В прошлом уроке ты отменял корутины, уводил блокирующий ввод-вывод в `withContext(Dispatchers.IO)` и следил, чтобы ошибки не терялись. Сервис выгружает отчёт из внешнего API, сорок страниц, каждая приходит примерно за секунду. Функция `suspend fun loadReport(): List<Page>` вернёт всё одним куском через сорок секунд, а пользователь всё это время смотрит на пустой экран. Хочется отдавать страницы по мере загрузки, не возвращаясь к колбэкам.

Для этого в kotlinx.coroutines есть Flow, асинхронный поток значений. Дальше в уроке «поток» — это всегда Flow, а thread мы называем потоком выполнения. Операторы у Flow те же `map` и `filter`, что у коллекций, и легко решить, что данные уже лежат в памяти. А по привычке из прошлого урока хочется сменить диспетчер через `withContext`. Компилятор не возразит ни в том, ни в другом случае, ошибки проявятся только при запуске.

После урока ты сможешь создать холодный поток через `flow`, `flowOf` и `asFlow`, собрать из операторов цепочку обработки, перенести работу источника на другой диспетчер через `flowOn`, перехватить ошибку через `catch` и выполнить завершающее действие в `onCompletion`.

## Ядро: Flow — Sequence, которая умеет ждать

<Callout type="purple" title="Суть">
**Flow** (поток) выдаёт несколько значений по одному и между ними может приостанавливаться: ждать сеть, диск или `delay`. Suspend-функция возвращает одно значение, Flow — сколько угодно, по мере готовности. Холодный поток, как и `Sequence`, **ленивый**: пока его не соберут **терминальным оператором** вроде `collect`, код внутри не выполняется.
</Callout>

Flow берут там, где данные приходят порциями или меняются со временем: страницы API, строки большого файла, показания датчика, состояние экрана.

Прежде чем раскрыть ответ, ответь сам, хотя бы про себя.

<Reveal q="Функция prices() помечена suspend, минуту опрашивает биржу и возвращает список из 60 цен разом. График должен рисоваться по мере поступления цен. Какой должна стать её сигнатура?">
`fun prices(): Flow<Int>`, причём без `suspend`. Список отдаётся целиком, когда готовы все 60 цен, а поток отдаёт каждую цену, как только она пришла. Вызов `prices()` ничего не ждёт, он только возвращает описание потока, поэтому `suspend` ему не нужен: приостанавливаться будут `collect` и код внутри потока.
</Reveal>

## Как устроено: холодный поток

Поток создают тремя способами. Построитель **`flow { }`** (flow builder) принимает блок кода, где значения отдаются вызовом `emit`, и внутри блока можно вызывать suspend-функции. `flowOf(1, 2, 3)` делает поток из готовых значений, `asFlow()` — из коллекции, диапазона или `Sequence`.

Всё это **источники** (emitter): начало цепочки, которое выдаёт значения. Забирает их **сборщик** (collector): терминальный оператор `collect` вызывает свою лямбду для каждого значения. Сам `collect` — suspend-функция, поэтому поток собирают внутри корутины, в примерах урока это `runBlocking`.

Все три способа дают **холодный поток** (cold flow): он начинает выдавать значения, только когда его собирают. Страницы отчёта из API, числа из диапазона `(1..5).asFlow()` — примеры такого потока. Список устроен наоборот: `listOf(1, 2, 3)` вычислен заранее и просто лежит в памяти.

Примеры урока запускаются в Playground на Kotlin 2.4.20 с kotlinx.coroutines 1.7.3. На актуальной 1.11.0 вывод такой же.

Ниже `pages()` «загружает» две страницы, а `main` собирает один и тот же поток дважды. Сначала предскажи, потом запускай.

<KotlinPlayground>

```kotlin
import kotlinx.coroutines.delay
import kotlinx.coroutines.flow.*
import kotlinx.coroutines.runBlocking

fun pages(): Flow<Int> = flow {
    for (page in 1..2) {
        println("Загружаю страницу $page")
        delay(100)
        emit(page)
    }
}

fun main() = runBlocking {
    val report = pages()
    println("Поток создан")
    report.collect { println("Первый: $it") }
    report.collect { println("Второй: $it") }
}
```

</KotlinPlayground>

<Reveal q="Сколько раз программа напечатает «Загружаю страницу 1»?">
Дважды. «Поток создан» появится первым: вызов `pages()` только описал работу. Потом каждый `collect` запускает блок `flow` с начала, с тем же циклом и той же загрузкой. Выданные значения поток не хранит, и каждый терминальный оператор запускает его заново со всеми побочными эффектами.
</Reveal>

Запусти, потом замени второй `collect` на `println(report.first())` и посмотри, сколько страниц загрузится во второй раз.

<Callout type="blue" title="Если знаешь Java — Flow не одноразовый, в отличие от Stream">
Stream в Java одноразовый: второй `toList()` на том же объекте бросает `IllegalStateException: stream has already been operated upon or closed`. Холодный Flow можно собирать сколько угодно, но каждый сбор повторяет всю работу: исключения не будет, будет второй запрос в сеть.
</Callout>

В отличие от последовательностей из урока про коллекции, у Flow лямбды операторов — suspend-функции, и в `map` можно ходить в сеть. Если вызвать suspend-функцию из `map` у последовательности, компилятор ответит «Suspension functions can only be called within coroutine body.» (Kotlin 2.4.20).

## Как устроено: цепочка операторов

Операторы Flow делятся на те же две группы, что операции у `Sequence`. **Промежуточные** (intermediate) возвращают новый поток и ничего не выполняют. **Терминальные** (terminal) запускают поток и ждут результата, поэтому `collect`, `toList`, `first` и `reduce` — suspend-функции.

| Оператор | Что делает | Для `flowOf(1, 2, 3)` |
| --- | --- | --- |
| `map { it * 10 }` | превращает каждое значение | 10, 20, 30 |
| `filter { it > 1 }` | пропускает подходящие | 2, 3 |
| `take(2)` | берёт первые N и отменяет источник | 1, 2 |
| `onEach { println(it) }` | действие с каждым значением | 1, 2, 3 |
| `transform { emit(it); emit(-it) }` | выдаёт на каждое значение сколько угодно своих, хоть ни одного | 1, -1, 2, -2, 3, -3 |
| `toList()` | собирает в список | [1, 2, 3] |
| `first()` | первое значение, дальше сбор отменяется | 1 |
| `reduce { a, b -> a + b }` | сворачивает в одно значение | 6 |

Первые пять промежуточные, последние три терминальные. Ещё один терминальный, `collect()` без лямбды, запускает поток и отбрасывает значения. Его ставят после `onEach`. В программе ниже `onEach` печатает каждое число от источника.

<KotlinPlayground>

```kotlin
import kotlinx.coroutines.flow.*
import kotlinx.coroutines.runBlocking

fun main() = runBlocking {
    val result = (1..5).asFlow()
        .onEach { println("взял $it") }
        .filter { it % 2 == 1 }
        .map { it * 10 }
        .take(2)
        .toList()
    println(result)
}
```

</KotlinPlayground>

<Reveal q="Какие строки «взял …» напечатает программа и что будет в списке?">
«взял 1», «взял 2», «взял 3» и `[10, 30]`. Каждое число проходит всю цепочку, прежде чем источник выдаст следующее. Двойку отсекает `filter`, поэтому второе значение для `take` даёт только тройка. Получив два значения, `take` отменяет источник, и до 4 и 5 дело не доходит.
</Reveal>

Запусти, потом замени `take(2)` на `take(3)`. А если убрать `take` совсем, что изменится в выводе?

## Как устроено: контекст потока

<Reveal q="Функция lines() построена на flow { } и читает файл блокирующим вызовом. Её собирают в корутине на главном потоке выполнения (thread). Где пойдёт чтение файла?">
Там же, на главном потоке выполнения, и всё остальное на нём будет ждать конца чтения. Холодный поток по умолчанию выполняется в контексте сборщика: в той корутине и на том диспетчере, где вызвали `collect`. Сам Flow диспетчер не выбирает. Блокирующий источник на `Dispatchers.IO` переносят явно.
</Reveal>

После прошлого урока рука тянется к `withContext(Dispatchers.IO)`. Внутри `flow { }` так нельзя: построитель требует, чтобы `emit` вызывался в том же контексте, где идёт сбор. Код ниже компилируется, но при запуске падает. Проверь.

<KotlinPlayground>

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun thread() = Thread.currentThread().name

fun lines(): Flow<String> = flow {
    withContext(Dispatchers.IO) {
        println("читаю в ${thread()}")
        emit("первая строка")
    }
}

fun main() = runBlocking {
    lines().collect { println("$it: ${thread()}") }
}
```

</KotlinPlayground>

Исключение начинается со слов «IllegalStateException: Flow invariant is violated» и заканчивается советом «Please refer to 'flow' documentation or use 'flowOn' instead». Документация запрещает внутри `flow` любую смену контекста, даже без смены диспетчера: `withContext(CoroutineName("чтение"))` из прошлого урока тоже упадёт.

Правильный путь — оператор **`flowOn`**. Он меняет контекст для всего, что стоит в цепочке выше него, а операторы ниже и сам `collect` остаются в контексте сборщика. Это правило называется **сохранением контекста** (context preservation): поток не протаскивает свой контекст вниз. Исправь пример: убери `withContext` и допиши `flowOn` после блока.

```kotlin
fun lines(): Flow<String> = flow {
    println("читаю в ${thread()}")
    emit("первая строка")
}.flowOn(Dispatchers.IO)
```

Теперь чтение идёт на потоке выполнения `DefaultDispatcher-worker`, а строка печатается на `main`. Имя пула не ошибка: `Dispatchers.IO` делит потоки выполнения с `Dispatchers.Default`. Хвост вроде `@coroutine#2` — номер корутины. Playground запускает код в режиме отладки, и kotlinx.coroutines дописывает номер к имени потока выполнения, как `CoroutineName` в прошлом уроке.

При смене диспетчера `flowOn` ставит между источником и сборщиком буфер, и источник может выдать несколько значений вперёд. Без смены диспетчера так же устроен **`buffer()`**: медленные источник и сборщик работают одновременно, и общее время сокращается.

## Ошибки в потоке: catch и onCompletion

Необработанное исключение из потока долетает до того, кто вызвал `collect`, и его можно поймать обычным `try`/`catch` вокруг сбора. Внутри цепочки его перехватывает оператор **`catch`**. Всё, что стоит выше оператора, — **верх цепочки** (upstream), всё, что ниже, — низ (downstream). `catch` ловит исключения из upstream и может выдать запасное значение через `emit`. **`onCompletion`** ничего не перехватывает, а только узнаёт, чем кончился поток: успехом, ошибкой или отменой. Этим он похож на блок `finally`. В его лямбду приходит причина: `null`, если всё прошло успешно.

<KotlinPlayground>

```kotlin
import kotlinx.coroutines.flow.*
import kotlinx.coroutines.runBlocking

fun main() = runBlocking {
    flowOf(4, 2, 0)
        .catch { println("Поймал: $it") }
        .onCompletion { println("Поток завершён") }
        .collect { println(8 / it) }
}
```

</KotlinPlayground>

<Reveal q="Деление на ноль случится внутри collect. Что напечатает программа?">
2, 4, «Поток завершён» и `ArithmeticException: / by zero`. «Поймал» не появится: `collect` стоит ниже `catch`, а `catch` видит только то, что выше. `onCompletion` получает ошибки и сверху, и снизу, поэтому успевает напечатать своё. Код, ошибки которого должен поймать `catch`, ставь выше него, например в `map` или `onEach`.
</Reveal>

Запусти, потом перенеси деление в `.map { 8 / it }` перед `catch`, а в `collect` оставь `println(it)`. Посмотри, кто теперь поймает исключение.

## Горячие потоки: StateFlow и SharedFlow

Все потоки выше холодные. **Горячий поток** (hot flow) живёт независимо от сборщиков: выдаёт значения, даже когда его никто не собирает, и все сборщики получают одни и те же значения. Сборщика горячего потока называют **подписчиком** (subscriber).

- **`SharedFlow`** рассылает значения всем подписчикам и подходит для событий: сообщений в чате, уведомлений. Создаётся через `MutableSharedFlow()`, параметр `replay` задаёт, сколько прошлых значений получит новый подписчик. По умолчанию ни одного.
- **`StateFlow`** всегда хранит одно текущее значение в свойстве `value`. Новый подписчик сразу получает его, а дальше — самое свежее значение. Быстрые промежуточные изменения медленный подписчик пропустит, а значение, равное текущему, не придёт вовсе. Так хранят состояние: прогресс загрузки, число товаров в корзине.

```kotlin
class Cart {
    private val _count = MutableStateFlow(0)
    val count: StateFlow<Int> = _count.asStateFlow()

    fun add() {
        _count.update { it + 1 }
    }
}
```

`update` вычисляет новое значение из текущего атомарно, и два одновременных `add` не потеряют единицу. Сбор горячего потока сам не заканчивается: `collect` у `cart.count` не вернёт управление, пока корутину подписчика не отменят.

## Как на практике

- **Меняй диспетчер через `flowOn`.** Ставь его сразу после источника с блокирующим вводом-выводом, например чтением файла. Обработка ниже останется в контексте сборщика.
- **Ставь `catch` ниже того, что может упасть.** Ошибки в лямбде `collect` лови `try`/`catch` вокруг сбора или перенеси этот код в `onEach` перед `catch`.
- **Уборку клади в `onCompletion`.** Он сработает при успехе, ошибке и отмене.

<Callout type="teal" title="Как принято">
Руководство Android по корутинам советует классам, которые загружают и обрабатывают данные, отдавать suspend-функции для разовых вызовов и `Flow` для данных, которые меняются со временем. Изменяемые типы наружу не отдают: `MutableStateFlow` живёт в `private val _count`, снаружи виден `StateFlow`. Документация Kotlin добавляет `asStateFlow()`: без него внешний код может привести `StateFlow` обратно к `MutableStateFlow` и поменять состояние.
</Callout>

## Три разбора

**Разбор 1. Отчёт, который грузится дважды.**
Сервис берёт поток строк отчёта `rows` из внешнего API, считает их через `rows.count()` для заголовка и собирает `rows.toList()` для таблицы. В логах API каждый отчёт запрашивается дважды. Поток холодный, а `count` и `toList` — два терминальных оператора, два полных прогона со всеми запросами. Ход: собрать один раз, `val list = rows.toList()`, и взять `list.size`. Вывод: если данные холодного потока нужны в нескольких местах, собери их в коллекцию.

**Разбор 2. `catch`, который прятал баги.**
Команда поставила в поток цен `.catch { }` с пустой лямбдой, чтобы сбой сети не ронял экран. Через месяц выяснилось, что так же молча глотался `NullPointerException` из разбора ответа: цены перестали обновляться, и никто не видел почему. Ход: обрабатывать в `catch` только ожидаемое, например `IOException`, выдавать запасное значение через `emit`, а остальное пробрасывать через `throw e`, как советует документация. Вывод: неожиданная ошибка должна падать громко.

**Разбор 3. Flow там, где ждать нечего.**
Разработчик полюбил операторы Flow и обрабатывает ими список настроек из памяти: `settings.asFlow().filter { … }.toList()`, а чтобы вызвать `toList`, оборачивает код в `runBlocking`. Но ждать нечего: ни сети, ни диска. Ход: те же `filter` и `map` есть у `List`, а ленивость, если она нужна, даёт `Sequence`. Вывод: Flow нужен, когда между значениями есть ожидание.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| `withContext(Dispatchers.IO)` вокруг `emit` | `IllegalStateException` при сборе | `flowOn(Dispatchers.IO)` после источника |
| Ждать, что `catch` поймает ошибку из `collect` | `catch` видит только upstream | `try`/`catch` вокруг сбора или код в `onEach` перед `catch` |
| Два терминальных оператора на одном холодном потоке | Вся работа, включая запросы, выполняется дважды | Один раз `toList()`, дальше список |
| Пустой `catch { }` | Прячет баги вместе со сбоями сети | Ловить ожидаемые исключения, остальные пробрасывать |
| Публичный `MutableStateFlow` | Менять состояние может кто угодно | `private val _state` и `asStateFlow()` наружу |
| Ждать, что `collect` у `StateFlow` вернёт управление | Код после `collect` не выполнится | Отменять корутину подписчика или брать `first()` |

## Практикум

<Practice title="Собери поток показаний датчика" checklist={["Опрос датчика уходит на Dispatchers.IO через flowOn, внутри flow нет withContext", "Сбойные показания отброшены через filter и до вывода не доходят", "catch стоит ниже map и выдаёт «датчик недоступен» через emit", "onCompletion стоит ниже catch, и «Готово» печатается последней строкой", "Программа печатает четыре температуры, «датчик недоступен» и «Готово»"]}>
Функция `readSensor()` опрашивает датчик блокирующим вызовом `Thread.sleep` и выдаёт температуры. Сбойные показания приходят как `-999`, а в конце датчик отключается с ошибкой. Собери в `main` цепочку, которая:

1. переносит опрос датчика на `Dispatchers.IO`;
2. отбрасывает сбойные `-999`;
3. превращает число в строку вида «21 °C»;
4. при отказе датчика выдаёт строку «датчик недоступен»;
5. последней строкой печатает «Готово».

<KotlinPlayground>

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun readSensor(): Flow<Int> = flow {
    val raw = listOf(21, -999, 23, 22, -999, 25)
    for (value in raw) {
        Thread.sleep(50)
        emit(value)
    }
    Thread.sleep(50)
    error("датчик отключился")
}

fun main() = runBlocking {
    // собери поток здесь
}
```

</KotlinPlayground>

<div slot="solution">
Рабочий вариант:

```kotlin
fun main() = runBlocking {
    readSensor()
        .flowOn(Dispatchers.IO)
        .filter { it != -999 }
        .map { "$it °C" }
        .catch { emit("датчик недоступен") }
        .onCompletion { println("Готово") }
        .collect { println(it) }
}
```

Программа печатает «21 °C», «23 °C», «22 °C», «25 °C», «датчик недоступен» и «Готово». `flowOn` стоит сразу после источника, поэтому на `Dispatchers.IO` уходит только опрос с `Thread.sleep`, а `filter` и `map` работают в `main`. `catch` выдаёт строку, поэтому стоит после `map`: выше `map` в потоке ещё числа, и там компилятор ответит «Argument type mismatch: actual type is 'String', but 'Int' was expected». Если поставить `onCompletion` выше `catch`, «Готово» напечатается раньше строки про датчик: `onCompletion` увидит ошибку первым.

Пауза перед `error` не случайна. Если источник за `flowOn` упадёт сразу после `emit`, корутину сборщика отменят, и показание, которое ещё лежит в буфере, может потеряться. Справочник `flowOn` такие потери прямо допускает.
</div>
</Practice>

<Callout type="teal" title="В работу">
Где в твоём проекте данные приходят порциями: страницы API, строки большого файла, колбэк, который вызывается много раз? Возьми одно такое место и набросай его на Flow: где источник, где `flowOn`, где `catch`. Через неделю вернись к тренажёрам и проверь, помнишь ли, что ловит `catch`.
</Callout>

## Шпаргалка

| Что | Коротко |
| --- | --- |
| Поток из кода | `flow { emit(x) }` |
| Из готовых значений | `flowOf(1, 2, 3)` |
| Из коллекции или диапазона | `list.asFlow()`, `(1..5).asFlow()` |
| Запустить | `collect { }`, `toList()`, `first()`, `reduce { }` внутри корутины |
| Холодный поток | каждый терминальный оператор — новый запуск |
| Сменить диспетчер | `.flowOn(Dispatchers.IO)`, действует на всё выше |
| Ошибки источника | `.catch { emit(запасное) }`, ловит только upstream |
| После завершения | `.onCompletion { cause -> }`, как `finally` |
| Состояние | `MutableStateFlow` внутри, `StateFlow` наружу |
| События | `MutableSharedFlow`, `replay` для новых подписчиков |
