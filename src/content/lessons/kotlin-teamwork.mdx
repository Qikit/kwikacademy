## Зачем это

В прошлом уроке ты чинил запахи кода маленькими шагами рефакторинга. Теперь эти шаги нужно отдать команде. Ты открываешь пулреквест (pull request): функция `calc` переименована в `deliveryCost` в двенадцати файлах, а по дороге в неё добавилась бесплатная доставка для заказов дороже 3000 рублей, и в условии стоит `>=` вместо `>`. Коммит один, сообщение «правки». Ревьюер пролистал шестьсот строк переименований и одобрил, не заметив `>=`. Через неделю заказы ровно на 3000 рублей уезжают без оплаты доставки, а `git revert` откатит условие только вместе с переименованиями: они в одном коммите.

Кажется, что аккуратные коммиты, номера версий и ревью — бюрократия, которая тормозит работу. Руководство Google по код-ревью утверждает обратное: маленькие изменения просматривают быстрее и внимательнее. И номер версии не формальность: он бережёт пользователей библиотеки от поломок, а у Kotlin есть ловушки, которых нет в Java, — имена параметров и значения по умолчанию.

После урока ты сможешь разбить работу на коммиты и подписать их по правилам git и Conventional Commits, выбрать следующую версию библиотеки по SemVer, заметить правки, которые ломают код её пользователей, и писать к пулреквестам замечания, которые помогают автору.

## Ядро: каждое изменение читает другой человек

<Callout type="purple" title="Суть">
Коммит, номер версии и пулреквест — сообщения другим людям. **Коммит** хранит одну логическую правку и объясняет, что изменилось и зачем. **Номер версии** по SemVer говорит пользователю библиотеки, сломается ли его код после обновления. **Код-ревью** (code review) — проверка изменения другим разработчиком до слияния, чтобы код проекта со временем становился здоровее: понятнее и проще в поддержке.
</Callout>

Отсюда правило: пиши для человека, который не был на созвоне и не знает, откуда в условии доставки взялось `>=`.

Прежде чем раскрыть ответ, ответь сам, хотя бы про себя.

<Reveal q="Ты пишешь свой проект один. Можно коммитить с сообщениями «wip» и «fix» — всё равно их никто не прочитает?">
Нет. Этот другой человек — ты сам через полгода, когда ищешь, где сломался расчёт, и видишь двадцать коммитов «fix». По руководству Google, описание изменения остаётся в истории навсегда и помогает будущим инженерам, иногда и самому автору. Себе будущему пиши так же подробно, как коллеге.
</Reveal>

## Как устроено: коммит и его сообщение

**Коммит** (commit) должен содержать одну логическую правку. Переименование функции во всём проекте — одна правка, хоть и в двенадцати файлах. Исправление ошибки округления вместе с тестом на неё — тоже одна. А переименование и исправление вместе дают две. По Pro Git, такие коммиты легче понять и откатить по одному. Если правки перемешались в одном файле, `git add --patch` добавит в коммит только выбранные куски.

Правила сообщения:

- заголовок — текст до первой пустой строки, одна строка примерно до 50 символов; git показывает его в истории;
- потом пустая строка и тело с переносом около 72 символов: зачем понадобилось изменение и чем новое поведение отличается от прежнего;
- повелительное наклонение, как в сообщениях, которые пишут сами `git merge` и `git revert`: «Fix bug», а не «Fixed bug» или «Fixes bug».

```text
Round fee down to whole kopecks

fee() rounded half up, so monthly reports differed
from the bank by a few rubles. Round down, as the
bank does.
```

**Conventional Commits** 1.0.0 — соглашение поверх этих правил: по сообщениям коммитов инструменты собирают список изменений и выбирают номер версии. Заголовок — это тип, необязательная **область** (scope) в скобках, необязательный `!`, двоеточие с пробелом и описание. Для новой возможности тип `feat` обязателен, для исправления ошибки — `fix`. Другие типы тоже разрешены, например `docs`. А работа в шляпе рефакторинга из прошлого урока уходит в отдельный коммит `refactor`.

```text
fix(billing): round fee down to whole kopecks
```

Изменение, которое ломает код пользователей, отмечают `!` перед двоеточием (п. 13) или **футером** (footer) `BREAKING CHANGE:` — строкой в конце сообщения после пустой строки:

```text
feat(api)!: require currency in fee()

BREAKING CHANGE: fee(amount) is removed, call
fee(amount, "RUB") instead.
```

`BREAKING CHANGE` пишут только заглавными, а регистр остального, например типа, инструменты учитывать не должны.

<Reveal q="Коммит «refactor: extract fee calculation» заодно поменял округление суммы. Что пострадает при выпуске версии, кроме честности истории?">
Номер версии. Инструмент по Conventional Commits поднимет PATCH за `fix`, а за `refactor` ничего, и по номеру новое округление не заметить. Тип выбирают по тому, что увидит пользователь, так что округлению нужен свой коммит `fix`.
</Reveal>

## Как устроено: номер версии

**Семантическое версионирование** (Semantic Versioning, SemVer) 2.0.0 требует объявить **публичный API**: номер версии рассказывает, как менялся именно он. Номер записывают как MAJOR.MINOR.PATCH:

| Что изменилось в API | Что поднять | От 1.4.2 |
| --- | --- | --- |
| Исправлена ошибка, API прежний | PATCH | 1.4.3 |
| Добавлено новое или помечено устаревшее | MINOR (п. 7), PATCH в ноль | 1.5.0 |
| Несовместимое изменение | MAJOR (п. 8), остальное в ноль | 2.0.0 |

С Conventional Commits это сходится: `fix` — PATCH, `feat` — MINOR, `BREAKING CHANGE` в коммите любого типа — MAJOR. В версиях 0.y.z «может измениться что угодно». Пре-релиз пишут через дефис, `2.0.0-rc.1` (rc — release candidate, кандидат в релиз), и он младше обычной `2.0.0`. Части номера растут как числа: 1.9.0, потом 1.10.0.

Программа ниже проверяет, вышло ли обновление; `zip` составляет пары из соответствующих частей двух версий. Предскажи вывод и не запускай, пока не ответишь на вопрос под кодом.

<KotlinPlayground>

```kotlin
fun isNewer(a: String, b: String): Boolean {
    val pairs = a.split(".").zip(b.split("."))
    for ((x, y) in pairs) {
        if (x.toInt() != y.toInt()) {
            return x.toInt() > y.toInt()
        }
    }
    return false
}

fun main() {
    val installed = "1.9.0"
    val latest = "1.10.0"
    println(latest > installed)
    println(isNewer(latest, installed))
}
```

</KotlinPlayground>

<Reveal q="Установлена версия 1.9.0, вышла 1.10.0. Что напечатают две строки в конце main?">
`false`, потом `true`. Оператор `>` у строк вызывает `compareTo`, а строки сравниваются посимвольно (лексикографически): после «1.» у одной идёт `'1'`, у другой `'9'`, и «1.10.0» оказывается меньше. `isNewer` сравнивает части как числа, этого и требует п. 11 SemVer.
</Reveal>

Запусти, потом замени `installed` на `"1.10.0-rc.1"`. Версия 1.10.0 старше своего пре-релиза, а программа упадёт с `NumberFormatException`: суффикс `-rc` к числу не приводится.

## Как устроено: что ломает код пользователей

Документация Kotlin для авторов библиотек различает виды **обратной совместимости** (backward compatibility). **Бинарная**: новая версия библиотеки подменяет старую, и уже скомпилированный код клиента работает. **По исходникам**: код клиента компилируется с новой версией без правок. Одну можно сломать, не задев другую.

В новой версии у публичной функции переименовали параметр, правка на вид безобидная. Этот код не скомпилируется — проверь:

<KotlinPlayground>

```kotlin
// в версии 1.x параметр назывался userId
fun notify(recipientId: Long) {
    println("Уведомление для $recipientId")
}

fun main() {
    notify(userId = 42)
}
```

</KotlinPlayground>

Среди ошибок будет «No parameter with name 'userId' found.» (Kotlin 2.4.20). Уже собранный код клиентов при этом работает: сломана совместимость по исходникам, и по SemVer это MAJOR.

<Callout type="blue" title="Если знаешь Java — имена параметров здесь часть API">
В Java аргументы передают только по позиции, и параметр публичного метода там переименовывают в любом релизе. В Kotlin вызов `notify(userId = 42)` называет параметр, поэтому имена параметров публичной функции меняй только в мажорной версии.
</Callout>

<Reveal q="Библиотека 1.4.2. К функции fee(amount: Long) добавили параметр currency со значением по умолчанию «RUB». Все вызовы у клиентов компилируются без правок. Можно выпускать 1.5.0?">
Если оставить так — нет. В байт-коде вместо `fee(long)` теперь `fee(long, String)`, и код, собранный со старой версией, упадёт с `NoSuchMethodError`. Так бывает, когда от 1.4.2 зависит другая библиотека. Выхода два: 2.0.0 с `BREAKING CHANGE` или старая функция рядом с новой, `fun fee(amount: Long): Long = fee(amount, "RUB")`, и тогда хватит 1.5.0.
</Reveal>

С Kotlin 2.4.0 старую сигнатуру сохранит и компилятор, если пометить новый параметр экспериментальной аннотацией `@IntroducedAt("1.5.0")`. А `@JvmOverloads` из урока про функции не спасает вызовы из Kotlin, которые уже пользовались значениями по умолчанию.

Устаревшее удаляют не сразу: его помечают `@Deprecated` и от релиза к релизу поднимают параметр `level`. `WARNING` даёт предупреждение, `ERROR` — ошибку компиляции, `HIDDEN` прячет объявление от кода, но оставляет в байт-коде. Руководство Kotlin растягивает этот путь на несколько минорных релизов, а удаляет объявление в мажорной версии. По строгому SemVer ошибка компиляции — уже MAJOR, и руководство оговаривает: стратегия может быть своей, но о ней сообщают пользователям.

## Как устроено: код-ревью

<Reveal q="Пулреквест исправляет ошибку, код стал понятнее, тест на ошибку есть. Но ты назвал бы переменную иначе и написал бы цикл через fold. Одобрить или вернуть?">
Одобрить. Стандарт Google: одобряй изменение, как только оно точно улучшает общее здоровье кода, даже если оно не идеально; идеального кода нет, есть код лучше. Мнение про имя и `fold` оставь с пометкой «Nit:», автор решит сам. Вернуть изменение можно за то, что код стал хуже, а вкус ревьюера для этого не повод.
</Reveal>

На ревью смотрят прежде всего на дизайн изменения, а ещё на функциональность с краевыми случаями и гонками потоков и на сложность, особенно на **переусложнение** (over-engineering): код решает задачи, которых ещё нет. Проверяют и тесты, имена, комментарии (им положено объяснять «почему») и стиль.

В вопросах стиля высший авторитет — руководство по стилю, а всё, чего в нём нет, — личное предпочтение. У Kotlin это соглашения о коде, и если их проверяют ktlint и detekt в сборке, как в уроке про стиль, про пробелы на ревью не пишут.

Вес замечания помечают словом в начале: «Nit:» — мелочь, «Optional:» — на выбор автора, «FYI:» — на будущее. А за удачное решение автора хвалят отдельным замечанием.

## Как на практике

- **Одна самостоятельная правка — один пулреквест.** Жёстких границ руководство Google не ставит, но 100 строк обычно в самый раз, а 1000 — обычно слишком много.
- **Отвечай на ревью в течение рабочего дня.** Но ради него не бросай сосредоточенную работу, дождись паузы.
- **Мелочи не гоняй по второму кругу.** Это LGTM with comments (LGTM — «looks good to me»): одобрить, а мелкие правки автор внесёт сам.
- **В библиотеке не меняй сигнатуры опубликованных функций.** Новая встаёт рядом, старая получает `@Deprecated`.

<Callout type="teal" title="Как принято">
В репозитории самого Kotlin, по руководству JetBrains, рефакторинги и переформатирование выносят в свои коммиты, чтобы ревьюер смотрел их отдельно от смысловых правок. Сообщение объясняет и что сделано, и почему, даже у рефакторинга: вместо голого «Make X lazy» пишут строкой ниже, что вычисление нетривиальное и часто не нужно.
</Callout>

## Три разбора

**Разбор 1. Библиотека застряла на 0.x.**
Внутренняя библиотека `money` третий год живёт на 0.x, а на ней работают пять сервисов в продакшене. В 0.y.z может измениться что угодно, и команды боятся обновляться. Ход: объявить публичный API и выпустить 1.0.0, ведь по FAQ SemVer софту в продакшене, вероятно, пора быть 1.0.0. Вывод: 0.y.z — только для начальной разработки.

**Разбор 2. Ревью на неделю.**
Ревьюер отвечает раз в три дня десятком замечаний про переносы и импорты, а пулреквест уже конфликтует с основной веткой. Ход: стиль отдать ktlint в сборке, вкусовое пометить «Nit:», отвечать в течение дня. Вывод: на ревьюера, строгого по существу, перестают жаловаться, когда он отвечает быстро.

**Разбор 3. Когда большой пулреквест — норма.**
Ты переименовал пакет рефакторингом IntelliJ IDEA, и правка задела 180 файлов; по частям переименование не соберётся. Google допускает большие изменения от инструмента рефакторинга, которому полностью доверяешь. Ход: отдельный пулреквест только с переименованием. Вывод: правило о размере бережёт внимание ревьюера, и где читать нечего, оно ослабевает.

## Типовые ошибки

| Ошибка | Почему вредит | Что вместо |
| --- | --- | --- |
| Коммит «правки» на пять задач | Нельзя понять и откатить по частям | Коммит на одну логическую правку |
| Рефакторинг и изменение поведения вместе | Ревьюер не видит, что поменялось по смыслу | Два коммита: `refactor:` и `fix:` |
| «Fixed rounding bug in fee calculation for EUR invoices» | Длиннее 50 символов и не в повелительном наклонении | «Round EUR fees down» |
| Сравнивать версии как строки | «1.10.0» окажется меньше «1.9.0» | Сравнивать части как числа |
| Параметр по умолчанию в опубликованной функции как MINOR | Собранный код клиентов падает с `NoSuchMethodError` | Старая функция рядом с новой или MAJOR |
| Блокировать пулреквест из-за вкуса | Автор ждёт, код лучше не становится | «Nit:» и одобрение |

## Практикум

<Practice title="Проверь пулреквест и напиши сообщение коммита" checklist={["Нашёл три вызова, где вывод расходится с SemVer и Conventional Commits, и назвал верную версию для каждого", "У каждой ошибки есть причина в коде и правило из SemVer или Conventional Commits", "Замечания говорят о коде, не об авторе, и в каждом есть «почему»", "Вкусовое помечено «Nit:», и есть замечание о том, что сделано хорошо", "Заголовок коммита по Conventional Commits, в повелительном наклонении, до 50 символов", "В теле коммита сказано, зачем нужна функция"]}>
Коллега прислал пулреквест: функция для скрипта релиза выбирает следующую версию по сообщениям коммитов. Запусти код и сравни вывод с тем, что требуют SemVer и Conventional Commits. Напиши замечания по правилам Google и сообщение коммита, с которым исправленная функция попадёт в основную ветку.

<KotlinPlayground>

```kotlin
fun nextVersion(
    current: String,
    commits: List<String>,
): String {
    val parts = current.split(".").map { it.toInt() }
    var major = parts[0]
    var minor = parts[1]
    var patch = parts[2]
    if (commits.any { it.contains("BREAKING CHANGE") }) {
        major++
        minor = 0
        patch = 0
    } else if (commits.any { it.startsWith("feat") }) {
        minor++
    } else if (commits.any { it.contains("fix") }) {
        patch++
    }
    return "$major.$minor.$patch"
}

fun main() {
    val v = "1.3.2"
    println(nextVersion(v, listOf("fix: round fee down")))
    println(nextVersion(v, listOf("feat: add EUR")))
    println(nextVersion(v, listOf("feat!: drop RUB")))
    println(nextVersion(v, listOf("docs: fix typo")))
}
```

</KotlinPlayground>

<div slot="solution">
Рабочий вариант. Программа печатает 1.4.2 вместо 1.4.0, 1.4.2 вместо 2.0.0 и 1.3.3 вместо прежней 1.3.2: ради одного `docs` релиз не нужен. Замечания:

- «`minor++` не обнуляет `patch`, и 1.3.2 с `feat` становится 1.4.2. По п. 7 SemVer при росте MINOR PATCH сбрасывается в 0.»
- «`feat!: drop RUB` даёт только MINOR, а по п. 13 Conventional Commits `!` перед двоеточием отмечает ломающее изменение: нужно 2.0.0.»
- «`contains("fix")` ищет слово во всём сообщении, и `docs: fix typo` поднимает PATCH. По Conventional Commits тип стоит в начале заголовка, до `:` или `(`, а `docs` на версию не влияет.»
- «Nit: цепочку `if`/`else if` на три ветки проще читать как `when`.»
- «Хорошо, что версия разбирается на числа: строкой её не сравнить.»

Сообщение коммита:

```text
feat(release): compute next version from commits

The release script asked for the version by hand,
and 1.4.0 once went out as 1.4.2. Derive MAJOR,
MINOR and PATCH from Conventional Commits types.
```

В исправленной функции `substringBefore(":")` берёт часть строки до двоеточия, а список раскладывается на переменные, как `data class`. `lowercase()` нужен, потому что регистр типа не важен; `BREAKING-CHANGE:` в футере — синоним `BREAKING CHANGE:`.

```kotlin
fun nextVersion(
    current: String,
    commits: List<String>,
): String {
    val (major, minor, patch) =
        current.split(".").map { it.toInt() }
    val heads = commits.map {
        it.substringBefore(":").lowercase()
    }
    val types = heads.map { it.substringBefore("(") }
    val breaking = heads.any { it.endsWith("!") } ||
        commits.any { "\nBREAKING CHANGE: " in it } ||
        commits.any { "\nBREAKING-CHANGE: " in it }
    return when {
        breaking -> "${major + 1}.0.0"
        "feat" in types -> "$major.${minor + 1}.0"
        "fix" in types -> "$major.$minor.${patch + 1}"
        else -> current
    }
}
```

## Шпаргалка

| Что | Коротко |
| --- | --- |
| Сообщение коммита | заголовок до ~50 символов, `Fix bug`; пустая строка; тело «зачем» |
| Conventional Commits | `тип(область)!: описание` |
| Версия от типа | `fix` → PATCH, `feat` → MINOR, остальные не влияют |
| Ломающее изменение | `!` перед `:` или футер `BREAKING CHANGE:` → MAJOR |
| SemVer | MAJOR.MINOR.PATCH, младшие части обнуляются |
| 0.y.z и пре-релиз | 0.y.z — API нестабилен; `2.0.0-rc.1` младше `2.0.0` |
| Библиотека на Kotlin | не меняй опубликованную сигнатуру, добавь функцию рядом |
| Ревью | одобряй, если код стал здоровее; `Nit:` для мелочей; ответ за рабочий день |
